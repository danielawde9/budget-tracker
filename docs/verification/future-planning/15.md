# Task 15 — Recurring gateway evidence

**Deliverable:** the typed application boundary for recurring bills/income —
DTOs, error classification, a Supabase gateway over task 14's 6 RPCs plus
the shared `find_planning_command`, and a state-machine hook generalizing
the goals/allocation gateway's accepted/ambiguous/retry pattern to 5
mutation kinds — per
`docs/superpowers/plans/future-planning/15-recurring-gateway.md`. Layer:
gateway/hooks only. No SQL, no visible screen edit.

## Process

Read every exact field list from `14-recurring-db.md` (command argument
lists, result fields, discriminators) first, then re-verified all seven
signatures and the `scheduled_occurrence_page` row shape directly against
the committed migration
(`supabase/migrations/20260914170000_recurring_schedules.sql`), per the
task's own "fix rounds changed a couple of things after the brief was
written — the migration is ground truth" instruction. No drift was found:
`confirm_scheduled_occurrence`'s seven arguments and
`scheduled_occurrence_page`'s 19 row fields both match the brief verbatim.
Read `12-goals-gateway.md` and its implementation
(`src/features/goals/{types,supabase-goals-gateway,use-goals,errors}.ts`) as
the explicit "most recent, most similar precedent" and matched its shape
closely: reused `planning-shared/rpc.ts`/`parse.ts` verbatim (task 07's own
instruction — "first implementation creates it, later gateways import it
without copying divergent money logic"); no new shared parser primitive was
needed this time (unlike task 12's `head`/`nullableHead` addition), since
recurring's mutation heads are all bigint revision/event ids, already
covered by `bigIntId`/`nullableBigIntId`/the gateway-local `bigIntArg`
helper goals already established.

## Task 1 — DTOs and the `RecurringGateway` method table

`types.ts` declares the exact 7 methods from the task's own table
(`loadOccurrences`→`scheduled_occurrence_page`, `saveSchedule`→
`save_schedule`, `materialize`→`materialize_schedule_occurrences`,
`setOccurrenceState`→`set_occurrence_state`, `confirm`→
`confirm_scheduled_occurrence`, `linkExisting`→`link_scheduled_payment`,
`findCommand`→`find_planning_command`) plus every DTO field the migration's
row/result shapes declare. `settledMinor`/`remainingMinor`/
`fundingShortfallMinor` are kept as independent fields, never derived
client-side from `expectedMinor` (the DB is the sole source of settlement
math); `overdue` is a separate boolean field, never inferred from `state`.
No generic arbitrary-RPC escape hatch is exposed — every method is its own
typed function calling exactly one RPC name.

## Task 2 — Validation and transport

Every response field goes through a boundary parser before the DTO is
trusted. Proved: the task's own monetary-fixture assertions
(`remainingMinor: '30000'` / `state: 'partial'` from a complete occurrence
row fixture), the `9007199254740993`-preserved/equivalent-unsafe-number-
rejected pair (on `sourceRevisionId`), a null required string field
(`id: null`), an unknown `state` enum (`'overdue'`), a duplicate occurrence
row, an invalid leap `dueDate` (`2025-02-29`), an incomplete two-part page
cursor (rejected client-side before ever calling the transport, mirroring
`scheduled_occurrence_page`'s own `(p_after_due_date is null) is distinct
from (p_after_id is null)` guard), a malformed effective date and a
non-canonical (floating-point-shaped) money string on `confirm` (both
rejected before the RPC call, not after a wasted round trip), and a
cross-space-shaped stale response (a `currency` value the DTO's own union
rejects). Every outgoing mutation argument is validated too:
`expectedRevisionId`/`expectedEventId` convert a text bigint id to a safe
JS number (or `null` when there is no prior head yet), money fields go
through `planningMoneyInput` (never a JS float), and `save_schedule`'s
`p_definition` is built key-for-key from task 14's exact list.

## Task 3 — Hook state machine

`useRecurring` generalizes `useGoals`/`useAllocation`'s accepted/ambiguous/
retry design across 5 mutation kinds via one `RetryCommand` union and a
`runCommandByKind` dispatcher. Its "current view" is the first page of
`scheduled_occurrence_page` for a given `(spaceId, fromDate, toDate)` — the
closest analogue to `useAllocation`'s `(spaceId, month, currency)` key,
since `loadOccurrences` has a date range instead of a month/currency axis —
while `loadMore` (pagination beyond the first page) is a stateless
passthrough, matching `loadDetail`/`loadHistory`/`loadMore`'s division of
responsibility in `useGoals`. Proved: stale-response discard on a space
change, load-error recovery via refresh, membership-loss clearing,
double-submit rejection (never double-posted), accepted-refresh-pending on
a failed post-commit read (exactly one command call, never reposted),
ambiguous-then-identical-retry (same request id both attempts), ambiguous
resolved silently once a receipt is found, a fresh command blocked while
ambiguous until explicitly cleared or reconciled, each of the 5 mutation
kinds reaching the gateway with its own freshly generated request id, and
`loadMore` filling in the current space/date-range. The real
15-second-timeout-through-fake-timers combination is not re-driven here for
the same documented reason as tasks 07/12's own suites (a known
jsdom/fake-timers/React-scheduler memory hazard, not a defect) — the shared
transport's own timeout is proved once, in isolation, by
`planning-shared/rpc.test.ts`.
