   through `scheduled_occurrence_page`'s `not funded.skipped` into a `null`

   (authenticated RPCs) *inside* `withRollback`, nesting a second
   `BEGIN`/`COMMIT` inside the harness's own open transaction — Postgres
   no-ops the inner `BEGIN` with a warning and the inner `COMMIT` actually
   commits the *outer* transaction early, dropping back to autocommit (and
   the default, non-authenticated role) for the rest of the test body. Fixed
   by moving all authenticated-RPC fixture setup (loan/category creation)
   to before the `withRollback` block, matching `goals-schema.integration.test.ts`'s
   own established pattern of using raw owner-role inserts, not RPC calls,

   role OIDs instead of names, always failing regardless of the real grants
   — fixed to use `has_function_privilege(role_name, oid, 'execute')`,
   this repo's own established pattern (`tests/db/categories.integration.test.ts`,
   `household-security.integration.test.ts`, `wallet-lifecycle.integration.test.ts`).

Two-connection race result: three independent two-real-connection races via
`orderedAuthenticatedRace` (two separate `pg.Client`s, never `Promise.all`
on one client): (1) two concurrent `confirm_scheduled_occurrence` calls on
the same occurrence with the same `p_expected_event_id` (both `null`) — the
second is blocked on the occurrence row's `FOR UPDATE` lock, then rejects
`40001` once it sees the first's committed event; exactly one
`financial_events` row results. (2) `reverse_financial_event` racing
`link_scheduled_payment` on the same original event, reverse committing
first — `link_scheduled_payment`'s own event-row lock (same lock order as
`reverse_financial_event`'s pre-existing `FOR UPDATE`) makes the link see
the committed reversal and reject `P0001` ("Reversed events cannot receive
new links"). (3) The same race with `link_scheduled_payment` committing
first — it succeeds, and the *subsequent* reversal still succeeds (it never
inspects `occurrence_events`); `private.schedule_occurrence_settlement`
correctly nets the occurrence back to `0` settled afterward, proving both
orderings are safe, per the task's explicit "prove both race orderings"
instruction.
