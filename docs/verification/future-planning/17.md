## Section 1 — the accounting calculation

`available = C − R − expenseCommitmentsMinor − debtCommitmentsMinor −
goalTopupsMinor − futureHeadroomMinor`, never clamped;
`deficitMinor = max(-available, 0)`. `C` reuses `private.goal_cash_pool`
(signed sum of all wallet movements through today, every wallet including
archived ones, both currencies independent). `R` reuses `private.
goal_space_earmarked_total` (raw earmark sum, uncapped by cash — a claim
can exceed available cash and does not clamp `available`, proved by the
literal `C20000,R50000,...,available-60000` fixture). Goal-bill coverage
(`private.planning_goal_bill_coverage`) allocates each purchase goal's
already-cash-capped `covered_minor` (from task 11's `goal_coverage_set`)
across its own linked unpaid occurrences, oldest `(due_date,id)` first, via
a window-function running sum — no per-goal loop, one indexed scan — proved
against the literal "one goal 30000, two bills 25000 each" fixture (25000
then 5000, 20000 uncovered). `Q_g = max(B_g,O_g) - min(G_g,max(B_g,O_g))`
is computed once per bucket (never by first summing B/O/G across buckets,
which does not distribute over this clamp-and-subtract shape) and proved
against all five literal acceptance-table rows, including the explicit
"not 0" row (`R=50000` must still subtract from `available` even though
`Q=0`).

## Section 2 — SQL helpers and exact RPCs

Both named helpers exist with the exact signatures given:
`private.planning_goal_bill_coverage(space,currency,as_of,horizon_end)` and
`private.planning_cash_commitments(space,currency,as_of)` (per-Future-group
bucket rows, plus a synthetic standalone `group_id null` row). Two
additional private helpers were added beyond the two named ones (permitted
— the brief names them as the *required* set, not an exhaustive one):
`private.planning_expense_buckets` (spending-side B/O/G/Q, group-aggregated
per the correction above) and `private.planning_materialization_gap` /
`private.planning_unpaid_backlog_count` (the two independent triggers
behind `incomplete`, sharing the response's one `unmaterializedCount`
field). All bound to ≤90-day windows; `planning_cash_commitments`'s debt
side computes `max(D_loan,O_debt_loan)` **per loan** (via `loan_monthly_
plan`'s per-loan figures joined to that loan's own unpaid `debt_payment`
occurrences) and sums — proved directly against the literal "reservation
10000, scheduled remaining 8000 → 10000, not 18000" fixture. `available_
cash_summary` and `cash_outlook` both exist with the exact signatures and
JSON key names from section 2, both `STABLE SECURITY DEFINER`, `set
search_path = pg_catalog, extensions`, `statement_timeout='10s'`, revoked
from PUBLIC/anon/authenticated/service_role then granted EXECUTE to
`authenticated` only — proved by a dedicated privilege-matrix test (below).
`spendableMinor`/`dailyExtraGuideMinor`/`daysRemaining` proved against the
literal "available 1001, 3 days → 333, not 334" fixture (floor division,
remainder retained, never rounded). `state` (`ready`/`unplanned`/
`incomplete`) nulls every derived commitment field and returns `groups: []`
whenever not `ready`, while still reporting `cashMinor`/`goalClaimsMinor`/
income-vs-spending/`uncategorizedMinor`/`daysRemaining`/
`unmaterializedCount` — the brief's own distinction between "cash/goal/bill
facts" (knowable without a plan) and `availableMinor` (the one number that
may never be guessed). `needsReview` extends task 11's `childPlanChanged`
check (income/root/goal-target current heads vs. the saved snapshot).
`cash_outlook`'s income line uses only unpaid **scheduled** income
occurrences, proved directly against the literal "monthly planned income
100000, no actual/scheduled salary, C10000 → never invents 100000" fixture;
goal earmarks are excluded from the cash line entirely (proved directly).

## EXPLAIN on a realistic 90-day fixture

Recorded in the `EXPLAIN on a realistic 90-day fixture` describe block
against a fixture with 3 spending groups (2 categories each), 1 Future
group, 2 goals, 1 loan, and 20 bills spread from 10 days overdue to ~70
days out (for `available_cash_summary`), and a second fixture with 15
income/expense schedules spread across 90 days (for `cash_outlook`). Both
RPCs are `SECURITY DEFINER` by the repo's own binding convention (`01-sql-
contract.md`: "Mark public reads STABLE DEFINER"), so the Postgres planner
never inlines their bodies into an outer `EXPLAIN` — inlining a DEFINER
function would silently change the effective privilege of its inner
queries, so this is a Postgres guarantee, not a gap in this evidence.
The outer `EXPLAIN (ANALYZE, BUFFERS)` therefore shows a single opaque
`Result` node, but its **actual total execution time** is real, measured
evidence: `available_cash_summary` completed in ~30ms (`shared hit=1534
read=10`), `cash_outlook` in ~6–9ms (`shared hit=608`), both far inside the
10-second `statement_timeout`. To also show index usage on the actual hot
path, the same-shaped queries `planning_expense_buckets` and the cash-pool
scan run internally were EXPLAINed directly (bypassing the DEFINER
boundary) against the identical fixture data:

- The unpaid-bill scan uses `Index Scan using scheduled_occurrences_page_idx`
  (`Index Cond: space_id = … AND due_date <= …`) joined via `Bitmap Heap
  Scan`/`Bitmap Index Scan` on `schedules_space_currency_idx` — 0.226ms.
- The cash-pool scan uses `Index Only Scan using
  financial_events_report_keyset_idx` (`Index Cond: space_id = … AND
  effective_date <= …`), `Bitmap Index Scan` on `wallet_movements_event_idx`,
  and an `Index Scan` on `wallets_id_space_id_key` (with a `Memoize` cache
  on the outer loop) — 0.074ms.

No sequential scan appears in either supplementary plan; both hot paths use
pre-existing indexes from earlier tasks (04/06/14), none new to this
migration (this task adds no tables, so no new indexes were needed).
