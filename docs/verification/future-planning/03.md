# Task 03 — Common planning SQL boundary evidence

**Deliverable:** shared parsers, an immutable receipt/replay ledger, and an
authorization/locking helper for later planning commands, per
`docs/superpowers/plans/future-planning/03-planning-foundation-db.md`. Layer:
database only. No UI or gateway change is part of this packet.

## Process

Written test-driven (`superpowers:test-driven-development`): the full test
file `tests/db/planning-command-foundation.integration.test.ts` was written
against the plan's exact SQL contracts before the migration existed, run once
to confirm every one of its 25 tests failed for the correct reason (`function
... does not exist`, `relation ... does not exist`, or — for the race test —
the pre-fix absence of serialization), then
`supabase/migrations/20260914100000_planning_command_foundation.sql` was
written using the plan's literal function/table bodies. All 25 passed on the
first implementation attempt; no forward-fix iteration was needed (unlike
task 02, this task's SQL was fully specified rather than requiring
discovery).

Two test-authoring mistakes were caught and fixed before that first
implementation run (neither is a defect in the plan's SQL):
- `expectSavepointRejection` requires an already-open transaction; the
  zero-row DELETE/TRUNCATE test needed wrapping in `withRollback`.
- The shared fixture space is `kind='personal'`, which a deferred trigger
  restricts to exactly one active member; the `find_planning_command`
  multi-actor test needed its own `household` space instead.

## Task 1 — parsers and immutable guards

`private.planning_minor` rejects: `null`, leading/trailing whitespace, a
leading `+` or `-` sign, a decimal point, exponent notation, a leading zero on
a multi-digit value, and a 16-digit value (the regex bounds money to 15
digits); it accepts `'0'` unless `p_positive` is `true`, and accepts the
maximum 15-digit value. All as a real Postgres function, not a regex unit
test in isolation.

`private.planning_reject_mutation` and `private.planning_guard_insert` are
proved through `public.planning_command_receipts` in Task 2, since Task 1 has
no table of its own to attach them to yet.

## Task 2 — receipt and lock helpers

- `private.planning_fingerprint` is deterministic for identical
  `(command, actor, payload)` and changes when the payload changes.
- `private.planning_replay`: returns `null` for an unknown request; returns
  the stored `result` on an exact `(command, actor, fingerprint)` match;
  raises `P0001 planning_idempotency_conflict` when any of those three
  differ; rejects `NULL` inputs with `22023`.
- `public.find_planning_command`: returns the caller's own receipt; returns
  `null` (not an error, and not the row) for a different active member's
  lookup of the same request; raises `42501 planning_not_authorized` for an
  outsider and for a member whose `space_memberships.status` was updated to
  `revoked` mid-test; raises `22023 planning_invalid_input` for a `null`
  request ID.
- A receipt insert inside a transaction that is rolled back leaves no row
  (plain transactional proof, not a special mechanism).
- **Layered defense proof** (01-test-recipes.md's "simulate the other
  layer's failure" pattern): inside a rolled-back transaction, `GRANT INSERT`
  and `GRANT USAGE` on the identity sequence to `authenticated`, plus a
  permissive `CREATE POLICY ... FOR INSERT ... WITH CHECK (true)`, were added
  — an authenticated insert still failed with `42501
  planning_command_required`, proving `planning_guard_insert`'s owner check
  is the actual backstop, not the privilege/RLS layer that would normally
  also block it.
- Zero-row `DELETE` and a whole-table `TRUNCATE` on
  `planning_command_receipts` both raise `42501 planning_history_immutable`
  (statement-level trigger; a zero-row match still fires it, matching the
  repo's documented Postgres lesson that row-level DELETE triggers do not).
- Inserting a receipt does not change the financial digest (events, wallet
  movements, loan postings) for the fixture space, using the exact digest
  query from `01-test-recipes.md`.

## Task 3 — existing setter lock integration

`private.set_monthly_budget_plan` was redefined (`CREATE OR REPLACE`, no
prior migration edited) to call `perform private.lock_planning_actor(p_space_id);`
after its existing validation and before its first advisory lock — taking the
`public.spaces` row lock ahead of the advisory locks, per `01-sql-contract.md`'s
ordering rule. Its signature, normalization, return shape, and fingerprint
computation are byte-for-byte unchanged from the version task 02 left it in.

Proved with `orderedAuthenticatedRace`: an income-plan write and an
expense-category-target write for the *same space* hash to *different*
existing advisory-lock keys (`plan_kind` and `category_id` both differ), so
before this task's change nothing serialized them. The race test holds the
first write's transaction open and proves the second genuinely blocks on it
before committing the first — confirming the new shared space lock, not
merely that the function still executes.
