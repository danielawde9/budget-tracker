**Deliverable:** the read-only "Available after commitments" human flow --
a compact per-currency Home card, a full per-currency Plan section
(headline figures, reservation breakdown table + bar, 60-day outlook chart
with a scenario switch), and route wiring -- per
`docs/superpowers/plans/future-planning/19-available-cash-ui.md`. Layer: UI
only. No SQL, posting gateway, auth, or loan logic changed. This completes
**Release 3** (bills and pay-cycle control, tasks 14-19).

## Task 1 — Flow and fixtures

Placement matches the brief exactly: `CashControlSummary` (compact variant)
renders once per currency inside a single `Available after commitments`
card on Home (`home-screen.tsx`'s new `CashControlCard`), and the full
detail (`CashControlSummary` full variant + `CommitmentBreakdown` +
`CashOutlookChart`) renders as `CashControlSection` x2 currencies inside
`PlanRoutes`, matching `AllocationCurrencySection`/`GoalsCurrencySection`'s
own `USD`/`LBP`-split pattern. The label is exactly "Available after
commitments"; the outlook is headed "Expected outlook" and is a visibly
separate component/section from the actual-cash figures, never replacing
them.

Every hook state has a distinct rendered state. Most of this coverage --
loading (skeleton, no fabricated `role="status"`/`role="alert"` on the
compact variant to avoid colliding with Home's own single status/alert
landmark -- proved by `routes.test.tsx`'s pre-existing singular
`getByRole('alert')`/`getByRole('status')` assertions continuing to pass
unmodified once `cashControl: null` was wired into every gateway fixture),
error+retry, ready, and `unplanned`/`incomplete` (never a fabricated
allowance) -- is proved with a **hand-constructed fake `CashReadSlice`
object** passed directly as a prop (`slice(...)` in `cash-control-
summary.test.tsx`, the local `slice()`/`renderChart()` helpers in
`cash-outlook-chart.test.tsx`), the identical pattern task 16's own
`upcoming-page.test.tsx` used and disclosed honestly ("proved directly...
with a fake `RecurringState`") -- neither of those two files' main
`describe` blocks imports or calls `useCashControl`, and neither
instantiates `InMemoryCashControlGateway`. (An earlier draft of this
document incorrectly claimed the real hook was wired throughout; corrected
here after an independent review caught the false claim -- see "Fix round
1" below.)

**Space-switch-while-loading and revoked-membership recovery are the two
exceptions**: the brief's own Task 1 instruction requires these at the
component layer specifically (a broader ask than tasks 13/16 made of
themselves, which deferred both entirely to the hook-level proof already on
file). A fake `CashReadSlice` prop cannot exercise either case -- both are
about the *hook's own* generation/abort and membership-loss bookkeeping,
which does not exist unless the real hook is actually mounted. Both files
therefore gained a second, dedicated `describe` block
(`HookWiredSummary`/`HookWiredChart`, added in the fix round below) that
mounts the real `useCashControl` hook -- with a custom deferred-promise
gateway for the space-switch case (the same technique task 18's own
`use-cash-control.test.tsx` uses) and `InMemoryCashControlGateway` for the
membership-loss case -- and renders its slice through the real
`CashControlSummary`/`CashOutlookChart` component, asserting the *rendered
DOM* discards the stale figure/assumption and recovers after a valid space
is selected. Task 18's own `use-cash-control.test.tsx` already proves the
underlying generation/abort/membership mechanics correct in isolation
(unchanged by this task); these four new tests prove specifically that the
mechanics surface correctly once wired into this task's own rendering
code, which is the part task 18 could not have proved and the part the
brief's Task 1 instruction is actually asking for.

**U19-01 through U19-05:**

- **U19-01** (cash 100000 minus commitments 110000 -> shortfall 10000) is
  proved in `cash-control-summary.test.tsx` (`availableMinor: '-10000'`
  renders as `-$100.00`, `deficitMinor: '10000'` renders as its own
  `$100.00` Shortfall line, `spendableMinor: '0'` renders separately) and
  live in `e2e/cash-control.visual.spec.ts`'s first test, with a fixture
  whose components sum exactly (`cash 100000 - R 30000 - Q_g 20000 - debt
  60000 = -10000`).
- **U19-02** (goal 30000 funding a bill 50000 reserves 50000 once, not
  80000) is proved directly in `commitment-breakdown.test.tsx` (a group
  fixture with `unpaidBillsMinor: '50000'`, `goalOverlapMinor: '30000'`,
  `commitmentMinor: '20000'` -- the already-deduplicated server value --
  renders `$500.00`/`$300.00`/`$200.00` as three distinct cells, never a
  summed `$800.00`) and live in the same e2e test (the group row is
  asserted to contain `$200.00` and not `$800.00`). Neither the component
  nor the e2e assertion re-derives the dedup arithmetic client-side -- both
  read the already-computed `commitmentMinor` field verbatim, per the
  brief's own framing of this test ("exercises reading the already-
  server-computed Q_g value correctly, not recomputing it client-side").
- **U19-03** (a paid bill leaves the forecast exactly once, not
  double-counted between the summary and the outlook) holds structurally --
  `cash-control-summary.tsx`'s reservation breakdown and
  `cash-outlook-chart.tsx`'s per-day table read two entirely independent
  DTOs (`AvailableCashSummary.groups`/`expenseCommitmentsMinor` vs.
  `CashOutlook.days[].expectedOutflowMinor`) computed server-side by two
  separate RPCs; nowhere in this UI's code does a value from one ever get
  added to, subtracted from, or compared against a value from the other --
  and is now also proved directly by a dedicated regression test
  (`cash-control-summary.test.tsx`, added in the fix round below): a
  $500.00 rent bill's "before payment" and "after payment" snapshots are
  rendered together through `CashControlSummary` + `CommitmentBreakdown` +
  `CashOutlookChart`, asserting the paid bill drops out of the group's
  unpaid-bills/commitment cells and out of the outlook's same-day
  projected-outflow cell simultaneously, while the hero `available` figure
  stays exactly `$1,000.00` before and after (paying an already-fully-
  committed bill moves money, it does not create or destroy it). The
  underlying server-side accounting property this reflects is already
  exhaustively proved at the DB layer in task 17's own acceptance tests;
  this test proves the UI-layer property specifically -- that this task's
  own rendering code never recombines the two independent DTOs into a
  double-counted figure -- which is what U19-03 actually asks this layer
  to guard.
- **U19-04** (unconfirmed salary never increases current available cash) is
  proved directly in `cash-control-summary.test.tsx` ("a large
  received-income figure is shown separately and never folds into the
  available/spendable figures": a `receivedIncomeMinor` of `9000000`, huge
  relative to every other figure in the fixture, is asserted to appear only
  in its own "This month so far" strip while the `.cc-metric--hero`
  available figure is asserted to equal `cashMinor` exactly and never
  contain the received-income text). This also holds structurally: the DTO
  itself defines `availableMinor` from `cashMinor` (posted movements only)
  minus reservations, never from `receivedIncomeMinor`, and this UI never
  computes `available` itself -- it only ever displays the field verbatim.
- **U19-05** (a partial month uses inclusive remaining days for the guide)
  is proved by rendering the exact `daysRemaining: 3`/`dailyExtraGuideMinor:
  '333'` fixture from `17-available-cash-db.md`'s own acceptance example
  (`cash-control-summary.test.tsx` and live in the e2e spec) and asserting
  the rendered guide and "3 remaining day(s)" text match verbatim -- no
  `Date`/day-count arithmetic exists anywhere in this feature's rendering
  path to recompute or contradict it.

## Task 2 — Screen and acceptance properties

`CashControlSummary`'s ready-state view shows four separately labelled
values that are never merged: `Actual cash` (`cashMinor`), the signed
`Available after commitments` hero figure (never clamped), `Spendable
(floored at zero)` (`spendableMinor`), and `Shortfall` (`deficitMinor`,
danger-colored only when nonzero). A "This month so far" strip
(`receivedIncomeMinor`/`ordinarySpendingMinor`/`incomeMinusSpendingMinor`)
is visually and semantically separate from all four, satisfying "actual
cash and expected income never combined into one balance." The reservation
breakdown lists every non-null commitment component
(`goalClaimsMinor`/`expenseCommitmentsMinor`/`debtCommitmentsMinor`/
`goalTopupsMinor`/`futureHeadroomMinor`) as its own labelled line, with
`Not applicable` (not a guessed `0`) for any field the DTO leaves `null`
outside `ready`. The daily guide is labelled exactly "Extra unassigned cash
per day" with the brief's own required explanation ("category budgets are
already reserved... not the whole grocery/transport allowance") and never
renders when `state !== 'ready'` (the DTO's own null contract plus an
explicit `state === 'ready'` guard as defense-in-depth). This view has no
Save or posting action anywhere -- every dialog/editor this task could have
opened (bill/goal/category) belongs to another feature's own files and is
out of scope; see `docs/decisions.md` for the exact drilldown-scope
reasoning.

`CommitmentBreakdown` is an accessible table (`Group`/`Budget remaining`/
`Unpaid bills`/`Covered by goal`/`Net reserved`/a "Details" drilldown
column) with a per-row bar. A Future-purpose group (`unpaidBillsMinor`/
`goalOverlapMinor` both `null`) shows `Not applicable` for those two
columns and no bar. The "Details" button expands a plain-language sentence
restating the same row's numbers in prose, satisfying "inspect every
reservation component" without a fabricated cross-feature navigation (see
`docs/decisions.md`, judgment 3).

`CashOutlookChart` shows the 60-day forecast as a per-day accessible table
with a signed bar, a scenario switch (`Expected income` /
`Conservative (no future income)`, local UI state only -- switching creates
no journal row, matching task 18's own "changing a scenario creates no
journal row" contract), the first projected shortfall date, and overdue
items explicitly labelled as "bucketed into today." It never renders a
chart when `state === 'incomplete'`, showing an explicit
materialization-needed message instead.

Use of `formatMinorAmount`/`<bdi>`/EN-AR copy/logical CSS properties/no new
chart library/no design-token replacement -- see Task 3 and the Process
section above for the specific `<bdi>` and shared-helper checks performed.

## Task 3 — Bars/charts with accessible data equivalents

`chart-ratio.ts`'s `chartPercent` is copied verbatim from the brief with
the identical 6-case unit-test suite goals/allocation/recurring all already
use, and exports nothing else. Per `docs/decisions.md`'s judgment 2, the
three required bar behaviours are each demonstrated in the one component
that genuinely exhibits that case in this DTO shape, rather than forced
into every component: `cash-control-summary.tsx`'s own bar is the
negative-value/zero-baseline/inverse-segment case (the signed `available`
figure, proved with a `-10000`-minor fixture rendering a visible red
inverse segment sized against total reservations); `commitment-
breakdown.tsx`'s per-row bar is the over-100%/visible-overflow case
(`budgetRemainingMinor: '20000'`, `unpaidBillsMinor: '30000'` ->
100%-clamped bar plus an exact `+$100.00` numeric overage, proved with a
dedicated unit test asserting the overage is computed from the original
`BigInt` values, not the clamped `chartPercent` coordinate); `cash-
outlook-chart.tsx`'s per-day bar is the signed-plot case (`chartPercent`
called with each day's absolute `closingCashMinor` magnitude, rendered on
the correct side of a zero baseline, proved with a fixture whose second day
goes negative). Every bar has a full accessible table alongside it (`dl`
for the summary's own headline figures, `<table>` for the other two) and
every group/day row is fully spelled out in text, not implied by color
alone -- color never encodes financial meaning (`cc-danger-text`/`cc-badge`
always carry their own text). Reduced-motion users get no animated bar
transition (`@media (prefers-reduced-motion: reduce)` disables
`.cc-progress > span`'s `transition`, the only animation in this feature).
Zero targets: since `AvailableCashGroupRow` carries no `hasPlan`-equivalent
field, `commitment-breakdown.tsx` does not fabricate a "No target vs
Explicit zero" split the DTO cannot support -- see `docs/decisions.md`
judgment 1 for the full reasoning and `groupCommitmentRatio`'s own doc
comment.

## Known limitation (documented, not silently accepted)

**The commitment breakdown's "Details" drilldown never opens the real
bill/goal/category editor** -- `available_cash_summary`'s `groups` array
carries a group (category-group) id/name only, never an individual bill or
goal id, so there is no single entity this UI could honestly open; and
Plan's sibling sections have no shared cross-section navigation mechanism
in this codebase to wire one through even if an id existed. See `docs/
decisions.md` judgment 3 for the full reasoning and the two different kinds
of future change (an SQL/gateway change, or an app-shell navigation change)
that would each independently unblock this, neither of which is a UI-only
task's call to make unilaterally.

**Zero targets do not distinguish "no target set" from "target fully
spent"** for a spending group, because `AvailableCashGroupRow` carries no
`hasPlan`-equivalent flag -- see `docs/decisions.md` judgment 1.

**Home's compact card issues one unused `cash_outlook` read per currency**
(reusing the full `useCashControl` hook rather than a lighter
`available`-only fetch) -- see `docs/decisions.md` judgment 4; a bounded,
cheap read-only RPC, not a correctness issue.
