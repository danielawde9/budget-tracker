# Task 16 — Recurring UI evidence

**Deliverable:** the upcoming-bills human flow — schedule creation, the
occurrence list with an accessible table+bar chart, occurrence detail
(skip/reopen, record/link a payment), and route wiring — per
`docs/superpowers/plans/future-planning/16-recurring-ui.md`. Layer: UI only.
No SQL, posting gateway, auth, or loan logic changed. This completes
**Release 3's B1** (bills and pay-cycle control, part 1 — tasks 14–16).

**Real Playwright testing — not just component tests against a mocked
hook — found and fixed two genuine defects, plus one bug in this task's own
test:**

- **A materialized occurrence's synthetic id in the e2e fixture was not a
  valid UUID** (`` `${scheduleId}-occ-1` ``, a UUID with a suffix
  string-appended). `scheduled_occurrence_page`'s own response parser
  (`uuid()` in `planning-shared/parse.ts`, unchanged, correctly doing its
  job) rejected it, throwing `Error: Invalid UUID for id.` inside
  `useRecurring`'s `load()` — root-caused by temporarily instrumenting
  `load()`'s own start/resolve/catch points with `console.log` (removed
  before commit; `git diff` on that file is empty) and forwarding the
  page's console to the test runner, which showed the request landing, the
  fixture correctly returning `createdCount: 1`, and then this exact
  exception on the client with no later successful reload. The end-to-end
  symptom was the occurrence list staying on its empty state after a
  successful "Refresh occurrences" click, which `upcoming-page.tsx` renders
  the same underlying content for as `accepted-refresh-pending` (materialize
  itself had already succeeded server-side; only the follow-up read
  failed) -- correctly reachable UI for a genuine read failure after a
  successful write, but not what a passing U16-03 run should have hit at
  all, and the actual trigger (a malformed id) was in this task's own test
  fixture, not the product's read path. A component test using the
  in-memory gateway could not have caught this because the in-memory
  gateway never round-trips through the real response parser at all — only
  a real (or realistically shaped) RPC response exercises
  `parseOccurrencePage`. Fixed in the fixture only
  (`e2e/fixtures/loans.ts`): materialized occurrence ids are now generated
  as proper synthetic UUIDs (`c0000000-0000-4000-8000-<counter>`), matching
  the convention every other synthetic id in that fixture file already
  uses.
- **`upcoming-page.tsx`'s occurrence table had no responsive "stacked card"
  layout below 420px** (unlike `allocation-bars.tsx`, whose own
  `@media (max-width: 420px)` block this task should have copied from the
  start but initially only copied the bar/overage styling, not the
  responsive-table block). On a 390px mobile viewport, the seven-column
  table's "Review" drilldown button sat far enough into the horizontally
  scrolling table that Playwright's scroll-then-click sequence intermittently
  left it beneath the section's own header buttons mid-scroll, failing the
  click with a genuine "element intercepts pointer events" error — a real
  layout defect a component test (which never lays out a viewport-width
  table) cannot see. Fixed by copying `allocation-bars.tsx`'s exact
  responsive-table-to-stacked-cards block into `recurring.css` (visually
  hidden `<thead>`, `display:block` rows, `data-label::before` labels).
- **This task's own Arabic e2e test asserted the English-formatted amount
  string (`$500.00`) after switching the UI to Arabic**, where
  `formatMinorAmount` correctly renders Arabic-Indic digits
  (`٥٠٠٫٠٠ USD`) — a bug in the test, not the product. Fixed by computing
  the expected string through the real `formatMinorAmount` helper instead
  of a hardcoded literal.
- **This task's own "skip and reopen" e2e test hit a Playwright strict-mode
  violation**, surfacing during the full `pnpm test:e2e` regression run:
  `detail.getByText('Upcoming')` uses Playwright's default case-insensitive
  substring matching, so it resolved both the `rec-badge-upcoming` status
  badge *and* the "Back to **upcoming** bills" button. A bug in the test,
  not the product — fixed with `{ exact: true }`.

## Task 1 — Flow and fixtures

`UpcomingBillsSection` mounts as its own `<section>` inside `PlanRoutes`,
alongside `PlanPage`/`AllocationCurrencySection`×2/`GoalsCurrencySection`×2
— not replacing any of them, matching task 08/13's own "is a view within
Plan" precedent. Unlike goals' per-currency split,
`scheduled_occurrence_page` has no currency axis of its own (occurrences of
different currencies intermix in one page), so this is one section, not
two; it uses a fixed 60-day-ahead window
(`todayIso()..todayIso()+60d`) reused verbatim by the explicit-refresh
`materialize` call.

**Rendering or opening the page never posts money.** `UpcomingPage` never
calls `recurring.materialize` except from the "Refresh occurrences" button's
own `onClick` — there is no effect anywhere in this feature that calls it.
Proved directly: `upcoming-page.test.tsx`'s U16-03 test mounts and remounts
the component and asserts `materialize` was never called by either mount,
only by an explicit click; `e2e/recurring.visual.spec.ts`'s own U16-03 test
proves the same live end-to-end (create a schedule → its success screen →
list still shows "No occurrences" → explicit Refresh click → the new
occurrence appears only then).

Every hook status
(`loading`/`ready`/`saving`/`accepted-refresh-pending`/`ambiguous`/`error`)
has a distinct rendered state, proved directly in `upcoming-page.test.tsx`
with a fake `RecurringState` (loading skeleton, empty-vs-loading distinct
text, error retry, refresh-pending banner, ambiguous check-again/dismiss,
disabled Refresh while saving). A stale-response-discard-on-space-change
test and a membership-loss test already exist in `use-recurring.test.tsx`
(proved at the hook level in task 15); per task 13's own precedent, these
two are not re-proved per-component here — the hook-level proof is the
right layer for something that is entirely about the hook's own
generation/abort bookkeeping, not about any of this task's rendering code.

**U16-01 through U16-05:**

- **U16-01** (expected 50000, paid 20000 → 30000 remaining) is proved three
  times at three layers: `upcoming-page.test.tsx` and `occurrence-detail.
  test.tsx` each define a local `row()` fixture helper carrying the exact
  same 50000/20000/30000 values as task 15's own `coreOccurrenceRowFixture`
  (a same-value, separately-typed fixture per file, not a shared import --
  `settlement-progress.test.ts` similarly re-derives U16-01's numbers as its
  own first case), and the same numbers are encoded directly into the live
  e2e fixture and asserted on the rendered detail page.
- **U16-02** (a January-31 monthly recurrence previews correctly at
  February month-end) holds structurally, not by re-deriving the server's
  date arithmetic: no `Date` object anywhere in this feature's rendering
  path ever touches an occurrence's own `dueDate` — every due date is the
  server's plain `YYYY-MM-DD` string, displayed verbatim, and
  `occurrenceBucket`'s upcoming-vs-due split is a plain string comparison.
  Proved with a `dueDate: '2026-02-28'` fixture row asserting the exact
  string renders and no shifted `2026-03-*` date ever appears
  (`upcoming-page.test.tsx`), reinforced live in the e2e spec.
- **U16-03** (opening the page twice creates no duplicate occurrence or
  payment) — see above; proved at both the component and e2e layers.
- **U16-04** (a confirm timeout reconciles the receipt and posts at most
  once) is proved at the hook level already (task 15's
  `use-recurring.test.tsx`: "treats an ambiguous command as already
  accepted once its receipt is visible, without retrying it"). This task
  proves the *UI plumbing* on top of that: `confirm-payment-dialog.test.tsx`
  and `occurrence-detail.test.tsx` both assert that a timeout-shaped
  rejection shows exactly one "Retry unchanged request" action (never a
  second, freshly-built Save), and that clicking it calls the hook's own
  `retryAmbiguous` — never re-invokes `confirm` with new values.
- **U16-05** (reversing a linked payment reopens the remaining amount)
  holds structurally — `remainingMinor` is always a DTO field read straight
  from the gateway, never derived or cached locally by this UI. Proved by
  re-rendering `OccurrenceDetail` with the *same* occurrence id across two
  different page snapshots (settled → partially reopened after a simulated
  reversal) and asserting the screen reflects the second snapshot's
  settled/remaining figures exactly, with no leftover value from the first.

## Task 2 — Screen and acceptance properties

`OccurrenceAmountsTable` (inside `occurrence-detail.tsx`, reused by
`upcoming-page.tsx`'s own per-row table cells) shows expected/settled/
remaining as three separate labelled values, never merged. Due date is
always the server's plain string. "Exact recurrence rule" is reviewable at
schedule-creation time in `ScheduleEditor` (cadence/interval/dates shown
back in a reviewable preview line before submit, matching every other
dialog's review-before-submit convention) — see "Known limitation" below
for why there is no *revise*-schedule view of the rule for an
already-existing schedule. Skip/Reopen and Record/Link payment are each a
deliberate action from `OccurrenceDetail`, never automatic; every dialog
(`ScheduleEditor`, `ConfirmPaymentDialog`) follows `archive-wallet-
dialog.tsx`'s exact shape: one submission path (Enter or the primary
button), disabled while pending (no double-submit — proved directly by
`pending`-disables-the-form tests in every dialog test file), an ambiguous
outcome offers an explicit same-payload retry rather than a second
differently-shaped Save, and a recoverable rejection preserves whatever the
user typed.

`ConfirmPaymentDialog` additionally gates on occurrence kind:
`allowConfirm={row.kind !== 'debt_payment'}` locks a debt-payment
occurrence to link-only mode with an explicit note directing to the loan's
own repayment flow — proved by a dedicated test asserting the "Record
payment" radio never renders for a `debt_payment` row. Category/loan/
funding-goal/preferred-wallet references are pasted ids, not pickers, the
same scope boundary `GoalPurchaseDialog` (task 13) already established.

## Task 3 — Bars/charts with accessible data equivalents

`chart-ratio.ts`'s `chartPercent` is copied verbatim from the brief with
the identical 6-case unit-test suite goals/allocation both already use, and
exports nothing else — the shared expected-vs-settled math
(`hasTarget`/`settledNegative`/`percent`/`over`/`overageMinor`) lives in its
own `settlement-progress.ts` (+ 4-case test) instead, so `chart-ratio.ts`
stays exactly the brief's given helper. `upcoming-page.tsx`'s occurrence
list is one accessible `<table>` with a per-row bar cell (`allocation-
bars.tsx`'s own shape); `occurrence-detail.tsx`'s `OccurrenceAmountsTable`
is the same idea for a single occurrence — both call `settlementProgress`
rather than duplicating the same `BigInt` comparisons, so a future change
to the negative-settled guard or overage logic can't silently drift between
the two call sites. Both compute overage from the original `BigInt`
settled/expected values, never the clamped `chartPercent` coordinate —
proved with a 150%-of-expected settlement fixture asserting the exact
numeric overage (`+$50.00`/`+$50.00 over expected`, each wrapped in its own
`<bdi>` since it is a DB-sourced amount like every other figure in these
two components) alongside the 100%-clamped bar. A negative settled amount
(defensively guarded, not reachable through any normal flow since
`expectedMinor` is contractually positive) renders in `rec-danger-text`
rather than a misleading bar. Reduced-motion users get no animated counting
(`@media (prefers-reduced-motion: reduce)` disables the bar's own width
transition, the only animation in this feature). Every "Review" button is
this table's own labelled drilldown into `OccurrenceDetail`; color alone
never encodes state — every status badge also carries its own text label,
matching every numeric figure beside it being spelled out in the table.

## Known limitation (documented, not silently accepted)

**`ScheduleEditor` supports schedule creation only — there is no revise/
pause/resume UI for an existing schedule.** `scheduled_occurrence_page` (the
only read RPC this task's gateway exposes) projects occurrence rows, not a
schedule's own cadence/interval/state/dates, and there is no
schedule-detail RPC to read those back. A revise UI built from an
occurrence row's `sourceRevisionId` could not honestly pre-fill the
recurrence rule it would be revising — worse than task 13's own "note/
monthly-amount/priority not shown in revise mode" gap, since here *nothing*
about the rule is reconstructable. Rather than build a misleading partial
revise form, this task scoped to exactly what the brief's Task 1 asks for
("create a monthly/weekly schedule"). `saveSchedule` already accepts
`expectedRevisionId` for a future revise UI once a schedule-detail
projection exists. See `docs/decisions.md` for the full reasoning and three
further scope decisions this task made.

**No occurrence-level correction/audit history browsing** (goals' own
`GoalDetail` has one via `loadHistory`) — task 14/15 project none, and
adding one is a SQL/gateway change out of this UI-only task's scope.

## Post-commit review fixes (this commit)

An independent reviewer session read commit `398510f` and confirmed the
money/loan-routing/idempotency logic sound and the `ScheduleEditor`
creation-only scope decision accurate (task 15's gateway genuinely has no
schedule-level read RPC). Two small, contained findings were fixed here,
both verified by re-running the full recurring suite (vitest + the e2e
spec) plus `typecheck`/`test:ui`/`build`/`git diff --check`:

1. **Two overage amounts were missing their `<bdi>` wrap**
   (`occurrence-detail.tsx`, `upcoming-page.tsx`) — every other amount in
   both files was already correctly wrapped; these two were missed. Fixed.
2. **The `hasTarget`/`percent`/`over`/`overageMinor` computation was
   duplicated** between `OccurrenceAmountsTable` and `upcoming-page.tsx`'s
   row map — same math, copy-pasted. Extracted into
   `settlement-progress.ts`'s `settlementProgress()` (a new small module,
   not added to `chart-ratio.ts`, which stays exactly the brief's given
   `chartPercent` helper per the task's own constraint), with a 4-case unit
   test; both call sites now share it.

Fixing the `<bdi>` wraps changed two overage spans from a flat text node to
`+<bdi>amount</bdi> label`, which broke two existing tests'
`getByText('+$50.00...')` assertions (`getByText` does not match text split
across element boundaries) — both updated to
`getByText('$50.00').closest('.rec-overage-text')` +
`toHaveTextContent(...)`, asserting the same rendered content precisely
rather than loosening the check.
