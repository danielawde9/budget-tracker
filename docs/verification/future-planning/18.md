# Task 18 — Cash-control gateway evidence

**Deliverable:** the typed, read-only application boundary for cash-control —
DTOs, error classification, a Supabase gateway over task 17's two projection
RPCs (`available_cash_summary`, `cash_outlook`), and a two-slice
loading/ready/error hook, per
`docs/superpowers/plans/future-planning/18-available-cash-gateway.md`. Layer:
gateway/hooks only. No SQL, no visible screen edit. Simpler than task 15/12's
gateways by design: read-only, 2 methods, no mutation/command/receipt/
idempotency machinery at all.

## Process

Read `18-available-cash-gateway.md` first, then `17-available-cash-db.md`'s
own field lists, then cross-checked both RPCs' exact argument lists and every
returned JSON key directly against the committed migration
(`supabase/migrations/20260914180000_available_cash_projection.sql`), per the

instruction. One real drift was confirmed: `cash_outlook`'s brief-listed
field set (`currency,startDate,scenario,assumption,days,firstNegativeDate,
state`) is missing `overdueCount`/`overdueMinor`, which the migration's
`jsonb_build_object` call does return (added during task 17's own fix
rounds) — both are now in `CashOutlook`. No other drift was found:
`available_cash_summary`'s 22 JSON keys and `cash_outlook`'s now-9 JSON keys
both otherwise match the brief verbatim, including every nullability rule
(`cashMinor`/`goalClaimsMinor`/`receivedIncomeMinor`/`ordinarySpendingMinor`/
`incomeMinusSpendingMinor`/`uncategorizedMinor`/`daysRemaining`/
`unmaterializedCount` always present; every other money field and `groups`
null/empty unless `state === 'ready'`).

Read `15-recurring-gateway.md` and its implementation
(`src/features/recurring/{types,supabase-recurring-gateway,use-recurring,
errors}.ts`, `src/test/in-memory-recurring-gateway.ts`) as the most recent,

## Task 1 — DTOs and the `CashControlGateway` method table

`types.ts` declares exactly the 2 methods from the task's own table
(`loadAvailable`→`available_cash_summary`, `loadOutlook`→`cash_outlook`) plus
every DTO field the migration's `jsonb_build_object` calls declare,
including the `overdueCount`/`overdueMinor` pair confirmed above. No generic
arbitrary-RPC escape hatch is exposed — each method is its own typed
function calling exactly one RPC name via the shared transport (confirmed:
`grep -n "planningRpc(client" supabase-cash-control-gateway.ts` shows exactly
2 call sites, one per RPC name literal; no `.rpc(` call appears outside
`planning-shared/rpc.ts` itself).

## Task 2 — Validation and transport

Every response field goes through a boundary parser before the DTO is
trusted; unknown required money is always an error, never a defaulted `0`
(proved directly: a fixture with `cashMinor` deleted entirely is rejected,
not silently treated as zero cash). Proved in
`supabase-cash-control-gateway.test.ts` (24 tests): the task's own monetary
fixture (`cashMinor: '100000', availableMinor: '-10000', spendableMinor:
'0', deficitMinor: '10000', state: 'ready'`) parses with
`availableMinor === '-10000'`/`spendableMinor === '0'` exactly as specified;
the `9007199254740993`-preserved/equivalent-unsafe-number-rejected pair (on
`snapshotId`/`cashMinor`); a null required money string; an unknown `state`
enum; duplicate group rows; more than the 12-group cap; an invalid leap
`asOf` date; a cross-space-shaped stale response (a `currency` the DTO's own
union rejects); a complete `unplanned`/`incomplete` fixture with every
reservation/available/spendable/guide field `null` and `groups: []`, never a
guessed default; `p_days` rejected client-side outside `[1,90]` before ever
calling the transport (mirroring `cash_outlook`'s own SQL guard, the same
way the recurring gateway rejects an incomplete page cursor up front); an
unsupported `scenario` rejected client-side too; a response day beyond the
90-day cap; duplicate day dates; an outlook `state` value (`'unplanned'`)
the narrower `CashOutlookState` union correctly rejects (`cash_outlook` has
no snapshot concept, so it only ever returns `ready`/`incomplete` — verified
against the migration's own `v_state` variable, which is never assigned
`'unplanned'`); and a transport error surfacing unmolested
(`{code: '22023'}`/`{code: '42501'}`), never swallowed.

## Task 3 — Read-only hook recovery

`useCashControl` returns two independent `loading|ready|error` slices —
`available` (keyed by `spaceId|currency|asOfDate`) and `outlook` (keyed by
`spaceId|currency|asOfDate|outlookDays|scenario`) — via one internal
`useCashReadSlice<T>` helper, since the task's own Task 3 says "capture
space/currency/date/scenario **and a request generation for each read**":
`loadAvailable` and `loadOutlook` are two unrelated reads that can go stale
on different triggers (only the scenario changing must reload the outlook
alone, never the summary), so each slice tracks its own generation counter
and `AbortController`, generalizing the single-list `loadedKey`/generation
guard `useRecurring`/`useGoals` use to two independent lists here. Exactly
`loading`/`ready`/`error` — no saving/accepted-refresh-pending/ambiguous
state or phantom writer method was added, since there is no command here to
make idempotent or reconcile. Membership loss clears that slice's own
visible data and delegates to `onSpaceUnavailable`, same as
`useRecurring`/`useGoals`. A failed read has no UUID/receipt; `refresh()`
just retries with the same captured parameters.

Proved in `use-cash-control.test.tsx` (10 tests, using deferred promises for
the stale-response races): both slices reaching `ready` together; each RPC
called with the exact captured parameters; the brief's own signed-deficit
monetary fixture surfacing unchanged; the daily-extra-guide `1001/3→333`
fixture relayed exactly as the server computed it — **constructed as a
literal fake-gateway JSON response in this hook test, not a DB-integration
fixture tied to a real day-count**, deliberately sidestepping task 17's own
documented pitfall (its evidence doc originally claimed a `1001/3→333` test
that didn't exist, and the first version added later used a fixed remainder
that didn't actually discriminate floor from round-to-nearest on most real
calendar days — moot here since the gateway never recomputes the guide, it
only parses the value the server already floor-divided); an `unplanned`/
`incomplete` fixture with every reservation field `null` and `groups: []`;
stale-response discard when the as-of date changes mid-flight (available
slice) and when only the scenario changes mid-flight (outlook slice) —
the latter also asserting `loadAvailable`'s own call count is unchanged,
proving a scenario change never touches the independent summary slice, i.e.
never creates a journal row because it is just a different read parameter;
load-error recovery via `refresh()`; a timeout-shaped transport failure
classified as a plain retryable `error` (never a fabricated ambiguous
state) and recovered via `refresh()`; and membership loss clearing both
slices' data (`groups: []`, `days: []`) and calling `onSpaceUnavailable`.

The real 15-second-timeout-through-fake-timers combination is not re-driven
here for the same documented reason as tasks 07/12/15's own suites (a known
jsdom/fake-timers/React-scheduler out-of-memory hazard in this sandbox, not
a defect) — the shared transport's own timeout is proved once, in
isolation, by `planning-shared/rpc.test.ts`, and re-affirmed here by the
"classifies a timeout-shaped transport failure..." test covering exactly
what the hook needs to prove about reconciling it (lands in `error`,
recovers via `refresh()`).
