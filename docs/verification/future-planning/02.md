# Task 02 — Reporting foundation verification evidence

**Deliverable:** real-PostgreSQL regression proof and minimal forward fixes for
`docs/superpowers/plans/future-planning/02-reporting-verification.md`. Layer:
database only. No UI, gateway, or live-account change is part of this packet.

## Hypotheses (source observations from the task file)

| ID | Hypothesis | Result |
| --- | --- | --- |
| H1 | `report_monthly_cash_summary` re-negates an already-signed reversal movement | **Confirmed and fixed** |
| H2 | `report_category_actual_vs_budget` groups actual spend by the exact tagged category instead of its root | **Confirmed and fixed** |
| H3 | `report_category_actual_vs_budget` uses invoker access while `monthly_budget_plan_revisions` SELECT is revoked | **Confirmed and fixed** |
| H4 | `monthly_budget_category_page` takes a `created_at` cursor but never returns one | **Confirmed; addressed via new `_v2` function, v1 kept for existing consumers** |

Two additional defects were found only by running real tests, not by reading
the source (the task file explicitly anticipates this: hypotheses are "not a
claim they were reproduced in this planning session"):

| ID | Defect found while proving H1–H4 | Result |
| --- | --- | --- |
| H5 | `report_monthly_cash_summary`'s three `sum(bigint)` aggregates return `numeric`, which does not match its declared `bigint` RETURNS TABLE columns (`structure of query does not match function result type`) | **Confirmed and fixed** |
| H6 | `report_category_actual_vs_budget`'s own `currency` OUT parameter is ambiguous against the bare `currency` column reference inside its `keys` CTE (`column reference "currency" is ambiguous`) | **Confirmed and fixed** |
| H7 | A `timestamptz` pagination cursor round-tripped through a JS client's `Date` object loses sub-millisecond precision, duplicating/dropping rows across a page boundary when two rows share a microsecond-precision `created_at` | **Confirmed and fixed** (v2 returns/accepts the cursor timestamp as `text`) |

Both H1 and H2's sign defect turned out to be the same mistake appearing
independently in two functions in `20260912102000_reporting_read_models.sql`;
the fix removes the erroneous re-negation in both places (`report_monthly_cash_summary`'s `normalized_amount`, `report_category_actual_vs_budget`'s `actuals` CTE), matching the sign convention already used correctly by `monthly_budget_currency_summary` and `monthly_budget_category_page`.

Root-only enforcement (task's V04 fixture) was not itself hypothesized as a
pre-existing bug in the task file's "source observations," but the task's own
fixture table requires it, and reading `private.set_monthly_budget_plan`
confirmed no such check existed. Added as a new confirmed forward change: an
application-level check in `private.set_monthly_budget_plan` plus an
independent `BEFORE INSERT` trigger on `monthly_budget_plan_revisions`
(`private.reject_subcategory_budget_target`), tested with both layers
(RPC rejection, then a direct owner-level INSERT bypassing the RPC entirely).
No existing row could violate this: the table has never been written to by a
live account.

## Fixture coverage (V01–V08 from the task file)

All eight fixtures are implemented as individual tests in
`tests/db/planning-projections.integration.test.ts`, each with its own
independent space (per the task's "not reused accumulating money" instruction):

- **V01** — USD income + same-day inverse → income `0`, wallet delta `0`. Pass.
- **V02** — August expense, September-dated reversal → August expense `5000`,
  September expense `-5000` (each period reflects its own recorded movement;
  the correction is not retroactively folded into the original period). Pass.
- **V03** — root target + subcategory expense → root actual `3000`, remaining
  `7000`; no separate row exists for the child category. Pass.
- **V04** — subcategory target rejected at the RPC (`P0001`, savepoint) and at
  the constraint layer via a direct owner INSERT bypassing the RPC. Pass.
- **V05** — `report_category_actual_vs_budget` succeeds for an authenticated
  member while `has_table_privilege('authenticated', 'public.monthly_budget_plan_revisions', 'SELECT')` is independently confirmed `false`. Pass.
- **V06** — outsider, a membership revoked mid-test, a null month, and a null
  `report_wallet_activity` page limit are each denied with `42501`. The null
  page-limit case is H-adjacent: `p_event_limit not between 1 and 100` is
  `NULL` (never `TRUE`) for an explicit `NULL`, which silently bypassed the
  cap before this packet added an explicit `p_event_limit is null` check. Pass.
- **V07** — 101 root categories with USD targets (created inside one
  transaction, so every row shares the exact same `now()`-based `created_at`:
  the strongest possible tie) page as 50/50/1 through
  `monthly_budget_category_page_v2` with zero duplicate `(category_id,
  currency)` keys across pages. Pass.
- **V08** — opening balance, a same-currency transfer, a USD→LBP exchange, and
  a cash loan borrow each leave `report_monthly_cash_summary`'s ordinary
  income/expense at `0` for the current period. Pass.

Plus a literal classification ratchet: every `pg_enum` label for
`public.financial_event_kind` (read from `pg_catalog.pg_enum`, not a cached
list) must appear in an explicit ordinary-income/ordinary-expense/transfer/
exchange/loan/opening/reversal map; an unclassified new enum value fails the
test until classified.

## Migration replay

`replayMigrations` in `tests/db/disposable-database.ts` replays every
`supabase/migrations/*.sql` file from empty on every run in this packet's own
test file (via `migrationFiles()`), which is how H5/H6's real syntax/type
defects were caught: they are runtime errors, not migration-apply-time errors,
so the file applied silently broken until a query actually exercised it.
