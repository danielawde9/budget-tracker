# Task 10 — Goal commands evidence

**Deliverable:** the atomic, authorized, request-idempotent RPC layer over
task 09's goal schema — `create_goal_plan`, `revise_goal_plan`,
`set_goal_monthly_target`, `set_goal_milestone_state`,
`record_goal_earmark`, `move_goal_earmark`, `reverse_goal_earmark`,
`link_goal_purchase`, plus the private `goal_financing_state`/
`goal_cash_pool` helpers, per
`docs/superpowers/plans/future-planning/10-goals-commands-db.md`. Layer:
database only. Depends on task 09. Closes Task 2/3/4 of the plan; Task 5
(tests) below.

## Process

Wrote the full migration first (all 8 RPCs plus the two private helpers and
a forward-fix to task 09's own `check_goal_earmark_event`), then
`tests/db/goal-commands.integration.test.ts` (45 tests: definitions,
revisions, monthly targets, milestone state, replay/idempotency, tenant and
auth boundaries, one space-lock race) and
`tests/db/goal-funding.integration.test.ts` (26 tests: `goal_financing_state`
and `goal_cash_pool` directly, every row of the task's own Task 5 numeric
table, and the funding edge cases — underfunded acknowledgement, backdated
timelines, target reduction, reversal-exceeds-reduced-target, concurrent
releases, cross-connection replay, cross-actor idempotency conflict).

Before writing any SQL, re-read `20260908103000_harden_reverse_financial_event.sql`
to confirm `reverse_financial_event` locks the original event `FOR UPDATE`
before creating its reversal row — the premise `link_goal_purchase`'s own
`FOR UPDATE` lock on the same row relies on for race-safety against a
concurrent reversal, per the task's own "if source has changed, verify this
premise before code" instruction.

Real-Postgres run found **three real defects**, all fixed before commit:

- **`goal_financing_state` referenced a column that doesn't exist.**
  `goal_earmark_lines` has no surrogate `id` (its primary key is
  `(event_id, goal_id)`); the head computation's
  `select max(id) into v_latest_event_id from goal_earmark_lines ...` needs
  `event_id`. This broke every call to `goal_financing_state` for *any*
  goal, including one with zero earmark activity, so it surfaced immediately
  on the first test exercising a `revise_goal_plan` close-with-zero-earmark
  path. Fixed to `select max(event_id) into v_latest_event_id ...`.
- **Two test-authoring mistakes**, not SQL defects: `headFor()` was called
  from inside an open `withAuthenticatedTransaction` block in two test
  helpers, so the `SET LOCAL ROLE authenticated` from that same transaction
  was still active when the helper queried `private.goal_financing_state` —
  correctly revoked from `authenticated` — producing `permission denied for
  function goal_financing_state`. Fixed by computing every expected-head
  value *before* entering the authenticated transaction, matching the
  pattern already used correctly elsewhere in the same file
  (`link_goal_purchase`'s and `reverse_goal_earmark`'s helpers).
- One test constructed an unrealizable scenario (a `reserve` dated earlier
  than a backdated expense — earmark events always carry the server's
  current date, so a reserve can never predate an already-recorded, already
  backdated expense) and was replaced with a scenario that is realizable
  through the RPC surface and covers the same formula edge case from a
  different angle (a *reversal* whose own business date precedes its
  original expense's date, proving `goal_financing_state` nets both flags
  correctly by today regardless of which one is chronologically earlier).
- A test that reversed a *reserve* event instead of the *release* event it
  meant to undo was fixed to reverse the release — reversing the original
  reserve on top of an already-completed release would have double-subtracted,
  which is not the scenario the task's own "reverse exceeds a reduced
  target" requirement describes.

## Task 1 — Command interfaces

All 8 RPCs take the exact argument list and return the exact result keys
from the task's own table (Task 1). JSONB definition/milestone payloads are
validated field-by-field before any cast: every `::date`, `::integer`,
`::numeric`, and `::uuid` cast on a jsonb-extracted value is preceded by a
`jsonb_typeof`/regex check (a malformed date or ordinal raises the
project's own `22023 planning_invalid_input`, never a raw Postgres cast
error), including the two milestone-array validation loops (shared shape
between `create_goal_plan` and `revise_goal_plan`) and the `goalId`/`head`
fields inside `reverse_goal_earmark`'s `p_expected_heads` and
`link_goal_purchase`'s `p_lines`. Malformed dates use PG17's built-in
`pg_input_is_valid(text, 'date')` rather than a try/catch subtransaction.

## Task 2 — Goal definitions and monthly targets

`create_goal_plan` enforces the 100-active-or-paused and 200-total
per-space-per-currency caps left open by task 09 (see that task's own
decisions.md entry), under the shared `lock_planning_actor` space lock.
`revise_goal_plan` compares the current head before validating, forbids
kind/currency changes, requires a zero remaining earmark to close, and
locks a milestone's `kind` once any checklist event exists for it — but
lets a never-touched milestone identity's kind change freely and lets a
milestone silently drop out of the current definition while its identity
and history rows stay intact for a later revision to re-include. Monthly
targets follow the same append-chain/predecessor pattern as the existing
category-target commands; a positive target requires an active goal, a
zero target does not (an explicit "clear the target" path stays open on a
paused goal). Milestone state transitions are restricted to a `checklist`
milestone present in the *current* definition, alternate `complete`/
`reopen`, and never touch goal money.

## Task 3 — Effective earmark balance and stale token

`private.goal_financing_state(goal_id, as_of)` reconstructs
`earmarked`/`fulfilled` from the raw ledger (`goal_earmark_lines`) netted
against purchase links and their reversals, each gated by its own event's
`effective_date <= as_of` — proved directly against a reversal dated
*before* its original expense (a valid state the journal allows), and
against a purchase link created against a backdated expense while later
funds were reserved only afterward (correctly rejected downstream in
`link_goal_purchase`, not by this helper). `head` is a SHA-256 over the
current revision id, latest earmark event id, latest purchase link's
`(created_at, id)`, count of reversals effective by `as_of`, and the two
computed amounts — refined from a bigint revision counter specifically
because a financial reversal changes a goal's balance without inserting any
new planning row. `private.goal_cash_pool` sums signed `wallet_movements`
for a space/currency as of a date with no per-wallet floor, proved against
mixed income/expense and currency isolation.

## Task 4 — Funding operations and constraints

**Forward-fix**, `CREATE OR REPLACE FUNCTION private.check_goal_earmark_event`
(task 09's own committed migration file is not edited): the ceiling check
(`event_contribution > 0 and running_balance > target - fulfilled`) now
excludes `operation = 'reverse'`, mirroring task 05's own fix to task 04's
`check_allocation_month`. Task 10's own spec requires a reversal to restore
previously released funding "because it corrects history, not new intent,"
even into a goal whose target has since been lowered below the restored
amount — task 09's check, written before this requirement existed, would
have wrongly rejected that legitimate reversal. The existing nonnegative
floor (`running_balance < 0`) is untouched and remains the sole backstop
against a reversal driving a balance negative.

`record_goal_earmark` loads `goal_financing_state` and compares the
expected head *before* validating the amount, exactly as task 03's
allocation commands do; concurrency safety for the documented "release the
same amount twice" race comes entirely from the existing
`lock_planning_actor` space-row lock (every command takes it first) — the
second caller blocks until the first commits, then reads the *now-stale*
head and is rejected with `40001`, never racing the balance itself.
`move_goal_earmark` never checks `accept_underfunded` against the cash pool
because moving a claim between goals cannot increase the space's total
claims (proved: combined earmark before and after a move is identical).
`link_goal_purchase` locks the original expense event `FOR UPDATE` (shared
row with `reverse_financial_event`, proving the race either commits the
link before a concurrent reversal or rejects the link after it, never
both) and its goal rows in sorted order, then reconstructs each goal's full
signed timeline — every earmark line, purchase link, and purchase-link
reversal, ordered by `(effective_date, sort_key)` — checking every
checkpoint from the expense's own date through today, not just today's
snapshot; a backdated expense linked against funds reserved only afterward
is rejected because the running balance is negative at the expense's own
checkpoint even though today's snapshot alone would look sufficient.

## Task 5 — Numeric scenarios and closure

Every row of the task's own numeric table has a dedicated test in
`goal-funding.integration.test.ts` (cash70000/reserve60000+30000 needing
acknowledgement; reserve20000/release5000 to earmarked15000; move5000
leaving combined claims unchanged; reserve100000/link40000 to
earmark60000/fulfilled40000 with zero new financial/wallet rows; reversing
that link to earmark100000/fulfilled0; a second 40000 link against a 50000
expense rejecting with no partial link or receipt; two concurrent
60000-releases where the first succeeds and the second is rejected as
stale, balance never negative; close-after-full-fulfillment then an
expense reversal retaining the closed definition while exposing the
restored earmark; an identical replay after the goal changed returning the
untouched original result; a different actor reusing a request id
rejecting as an idempotency conflict). Plus: an ordinary later cash drop
below the earmark total (advisory only, no retroactive rejection); a
same-request race across two live connections both landing on the one
committed receipt; a target reduction that retains prior earmark history
and blocks further reserves past the new ceiling; a reversal legitimately
exceeding a since-reduced target; a zero-row `TRUNCATE` on a leaf earmark
table (task 09's own lesson, re-proved through the command layer); a
second reversal of an already-reversed event; an over-release; a reserve
into a paused goal; an allowed release out of a paused goal; a stale head
on `record_goal_earmark`; a link against an already-reversed expense; and a
loan-linked event rejected from `link_goal_purchase`.
