# Task 06 — Allocation projections evidence

**Deliverable:** `private.planning_ordinary_activity` plus four public
read-only reconciliation contracts (`allocation_month_state`,
`allocation_category_page`, `allocation_history_page`, `allocation_trend`),
per `docs/superpowers/plans/future-planning/06-allocation-projections-db.md`.
Layer: database only. No write path, no UI/gateway edit — task 06 explicitly
exits before the gateway.

## Process

Built test-first, one function at a time, against
`tests/db/allocation-projections.integration.test.ts` (25 tests): the
canonical ordinary-activity helper first (exact given SQL, wrapped with
membership and the 1–366-day range check), then `allocation_month_state`,
`allocation_category_page`, `allocation_history_page`, and `allocation_trend`
in the task's own Task 2 order. Two real defects were found only by running
against a real disposable Postgres, not by re-reading the plan's SQL:

- **Postgres has no builtin `max()`/`min()` aggregate for `uuid`.**
  `allocation_category_page`'s pagination originally computed its next-cursor
  UUID with `max(root_id) filter (where rn = p_limit)`, which fails at
  execution with `function max(uuid) does not exist` (Postgres does not
  validate a `plpgsql` function body's inner SQL until a given branch first
  runs). Fixed by restructuring the query around a `numbered` CTE and plain
  scalar subqueries (`(select root_id from numbered where rn = p_limit)`,
  `exists(select 1 from numbered where rn > p_limit)` for `hasMore`) instead
  of aggregating a UUID column.
- `SET statement_timeout='10s'` from the task's own Task 2 preamble was
  missing from the first draft of all four public functions; added to match
  task 03's established pattern (`set search_path=... set
  statement_timeout='10s'`).

Two test-fixture mistakes were also caught and fixed during the same run
(not SQL defects): a stale-revision test (`V09`) called
`set_monthly_category_target` with `expectedRevisionId: null` after a
revision already existed for that root (from the earlier publish), which
correctly raised `the monthly budget plan has changed` — fixed by reading
the root's actual current `target_revision_id` from
`allocation_month_roots` and passing it forward. A history-page pagination
test that republished the same month five times in a row hit the same
stale-income-revision check for the same reason — fixed by chaining each
publish's returned `incomeRevisionId` into the next call's
`expectedIncomeRevisionId`.

## Task 2 — Public read contracts

**`allocation_month_state`** — proved against the plan-pack's own Task 3
fixture exactly: 200000 planned, 180000 received, Essentials
target 112000/actual 118000, Lifestyle target 48000/actual 43000, Future
target 40000/debt 15000 ⇒ `expenseMinor` 161000, `incomeAfterSpendingMinor`
19000, `incomeAfterSpendingMinor - ownDebtPaidMinor` = 4000 (afterDebt),
Essentials variance −6000, Lifestyle variance +5000, no currency mixing (an
LBP-wallet expense recorded in the same space/month never touches the USD
header). Also proved: a subcategory expense rolling into its mapped root's
group actual; `hasPlan=false` with only synthetic unmapped/uncategorized
rows when no month was ever published; a zero-income/zero-group snapshot
reading back cleanly; a negative-correction month (a reversal landing in a
later month than its original expense) keeping the actual **signed**, not
floored at zero; live actual income changing on every read without flipping
`childPlanChanged`; two adjacent months' snapshots staying fully isolated
from each other in both the header and `allocation_history_page`;
`childPlanChanged` flipping true the moment a root target is edited directly
after publish without republishing; a foreign snapshot ID rejected even
though the month/currency exist; outsider and revoked-member denial; and a
null/non-normalized month rejected.

**`allocation_category_page`** — proved: pagination of 101 roots in one
group with identical total row count (101) and identical summed
`targetMinor` (101000) regardless of page size (10/25/100); an archived
historical root still resolving its name and stored amounts (no
`archived_at is null` filter on the category join, by design — the snapshot
owns the historical mapping); a foreign snapshot ID rejected even with a
group filter that would otherwise return nothing; a malformed (non-UUID)
cursor rejected at the type layer (`22P02`); the `1..100` limit bound; and
outsider denial.

**`allocation_history_page`** — proved: five successive publishes for the
same month page newest-first with a correct `nextId` cursor and `hasMore`
transition from true to false, with zero duplicate/missing rows across the
boundary; the `1..100` limit bound; and revoked-member denial.

**`allocation_trend`** — proved: three consecutive months where the middle
month has real activity but was never published (`generate_series` still
seeds it, `hasPlan=false`, live income/expense totals present, no snapshot
leak); a fully empty space/month/currency combination returning one
all-zero, `hasPlan=false` row rather than an empty array; the `1..12`
`p_month_count` bound (rejects 0, 13, and null); and outsider denial.
