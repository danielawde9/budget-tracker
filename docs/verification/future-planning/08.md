   over-allocation guard (a group's assigned category targets exceeding its

   invoke the same handler), and pending/error states that preserve every
   entered value. 13 tests, including exact submission-shape assertions for

## A genuine bug found only by testing in a real browser

The first `e2e/allocation.visual.spec.ts` run on the `mobile` (390px)
Playwright project failed `expectContainedControls` (the project's shared
"no control overflows the viewport" assertion): the bars table's
"View <group> categories" buttons rendered twice, both past the right edge
of a 390px viewport. Root cause: `.alloc-bars { overflow-x: auto; }` let the
literal `<table>` lay out at its natural (wide) width and scroll instead of
reflowing, so every control past the visible columns was technically present
but off-screen — exactly the overflow this project's own accessibility
contract exists to catch. Fixed with a `@media (max-width: 420px)` block
that turns the table into a column of "cards" (each `<td>` becomes a
flex row with its `data-label` shown via `content: attr(data-label)`) while
keeping the same DOM/accessibility tree — no duplicate markup, no
`display: none` on any data. Re-verified: all 6 mobile-project tests pass,
and the rendered screenshot was inspected by hand (see below).

## Live-browser verification

The real Supabase project has none of tasks 02–06's migrations deployed
(`pnpm migrate:live` has not been run this session). Logging in with the
live credential and opening Plan reproduces a pre-existing, unrelated
failure — "Could not load the monthly plan." / "The database row is missing
name_ar." — confirmed present on `main` before this task's commits and out
of Release 1's scope. This blocks verifying the new allocation section
against real production data today (the existing `PlanPage`'s error state
returns before `AllocationSetup` ever renders).

Full verification therefore used the project's own established e2e visual
pattern: `e2e/fixtures/loans.ts`'s Playwright route-interception fixture
(the same harness every other `*.visual.spec.ts` file uses) was extended
with handlers for `allocation_month_state`, `allocation_category_page`,
`allocation_history_page`, `allocation_trend`, `save_allocation_template`
(idempotent by request id, like the real RPC), `publish_allocation_month`
(same, and reuses the real `allocateIncome` helper so its preview numbers
are exactly what the real SQL would compute), and `find_planning_command`.
This exercises the real bundled app, a real Chrome browser, and the real
Supabase-js/PostgREST network path — fixture data appears only at the HTTP
boundary, exactly like every other visual spec in this repo.

`e2e/allocation.visual.spec.ts` (6 tests × 2 projects = 12): the exact
plan-pack Task 3 fixture renders correctly (U08-01: 200000/180000/161000/19000,
Essentials/Lifestyle/Future rows, the future row's paid/allocated label); a
month with no plan shows "Set up" and an honest empty message, not a crash;
a manual-mode setup submits and the overview updates to reflect it, without
reposting; a percentage-mode setup with a mapped category submits correctly
(U08-02-shaped: verified separately at the unit level with the literal
57/24/20 fixture, since the e2e fixture's own apportionment isn't the
subject under test there); the drilldown dialog opens with real category
rows; Arabic RTL mirrors the overview correctly, including translated
group/synthetic-row labels and `<bdi>`-isolated amounts (inspected by hand
in the rendered screenshot, not just asserted).

**Inspected by hand (screenshots read directly, not just measured):** desktop
(1440px) and mobile (390px) renders of the core fixture, and the Arabic RTL
mobile render. All three look correct: progress bars scale and color
(never color-alone) correctly including the over-100% red bar, the
responsive card layout is legible with no clipped controls, and Arabic
labels/amounts/directionality are all correct. 320px/768px/200%-zoom/
keyboard-only were not separately captured as screenshots this session
(synthetic-fixture time budget); the responsive CSS uses only a single
420px breakpoint plus relative units, so 320px is covered by the same rule
as 390px and 768px by the unconstrained desktop layout, but this is a
disclosed gap, not a claimed pass.
