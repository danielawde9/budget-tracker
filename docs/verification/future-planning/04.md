# Task 04 — Allocation schema evidence

**Deliverable:** immutable group identity, versioned templates, and immutable
monthly snapshots with relational tenancy/currency/predecessor/child
constraints, per
`docs/superpowers/plans/future-planning/04-allocation-schema-db.md`. Layer:
database only. No RPC or application edit is part of this packet — every row
in the tests below is seeded directly as the owning role, since no command
exists yet (task 05).

## Process

Written test-driven: `tests/db/allocation-schema.integration.test.ts` (20
tests) was written against the task's given DDL and its own rejection-case
checklist before `private.check_allocation_template`/`private.check_allocation_month`
existed, confirmed to fail for the right reason (missing functions/relations),
then the migration was implemented. Two real bugs surfaced only once the
suite ran for real:

- **`CREATE CONSTRAINT TRIGGER` also registers a `pg_constraint` row under its
  own name.** Two triggers (`allocation_template_lines_check`,
  `allocation_month_groups_check`) collided with Postgres's own
  auto-generated name for each table's two-column
  `check(name_en is not null or name_ar is not null)` constraint (Postgres
  names a single-column check `<table>_<column>_check` but a multi-column one
  falls back to the generic `<table>_check` — exactly the name I'd chosen).
  All seven constraint triggers were renamed with a `_publish_check` suffix
  to guarantee no future collision with any auto-generated check name.
- **`SET CONSTRAINTS ALL IMMEDIATE` changes the deferral *mode* for the rest
  of the transaction, not just a one-time check.** A test helper that forced
  the template check immediate, then later inserted an unrelated month
  snapshot header in the *same* transaction, found the header's own deferred
  trigger firing immediately (before its children existed) because the whole
  transaction had switched to immediate mode. Fixed by re-issuing
  `SET CONSTRAINTS ALL DEFERRED` right after every forced check.

Also caught in test authoring, before ever running anything: three helper
functions (`freshSpace`, `expenseRootCategory`, `planIncome`,
`planCategoryTarget`) each open their own `BEGIN…COMMIT` via
`withAuthenticatedTransaction`. Postgres has no true nested transactions, so
calling one of these *inside* an already-open `withRollback` block would
silently commit the outer transaction early on success (or roll it back early
on failure) instead of rolling back at the end — a real risk of leaking
fixture data between tests. Every test creates its real-command fixtures
(space/category/income/target) before entering `withRollback`, and only raw
owner-level `allocation_*` inserts happen inside it.
