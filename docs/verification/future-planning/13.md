# Task 13 — Goals UI evidence

**Deliverable:** the goals human flow — list/filter, create/revise editor
with an inline milestone sub-editor, detail view (coverage metrics,
progress bar, milestone checklist, correction history), funding
(reserve/release/move) and purchase-link dialogs, and route wiring — per
`docs/superpowers/plans/future-planning/13-goals-ui.md`. Layer: UI only. No
SQL, posting gateway, auth, or loan logic changed. This completes
**Release 2** (tasks 09–13).

## Process

Read the allocation UI (task 08) in full before writing anything — `DialogShell`,
one representative dialog (`archive-wallet-dialog.tsx`'s review/confirm/
success/ambiguous-retry shape), `allocation-bars.tsx`/`allocation-overview.tsx`/
`allocation-setup.tsx`, `allocation.css`, and the route/e2e-fixture wiring —
then mirrored every reusable convention (`t(locale, en, ar)` inline copy,
`.cr-card`/`.cr-button` visual language, `goal-*`-prefixed CSS instead of
`alloc-*`, the `unavailableXGateway`/`XCurrencySection` route-wiring
pattern) rather than inventing new ones. Built file by file: `chart-ratio.ts`
(copied verbatim, byte-identical to the given helper), `goal-milestones.tsx`,
`goal-funding-dialog.tsx`, `goal-purchase-dialog.tsx`, `goal-editor.tsx`,
`goal-detail.tsx`, `goals-page.tsx`, `goals.css`, route wiring, then
`e2e/goals.visual.spec.ts` (12 tests: 6 authored x desktop/mobile, matching
task 08's own density) plus the matching `e2e/fixtures/loans.ts` additions.

The real Playwright run against a live Chrome instance — not just component
tests against mocked hook state — found three genuine defects unit tests
could not have caught, exactly the reason "Always Playwright-test" is a
standing rule in this session:

- **`GoalDetail`'s own data-fetch effect depended on the whole `props.goals`
  object**, not the specific stable methods it calls. `useGoals` returns a
  fresh object literal every render (matching `useAllocation`'s own
  precedent, which never hit this because no allocation view does a second,
  nested fetch off the hook's return value); every status transition during
  a mutation (`saving` → `ready`/`ambiguous`) therefore recreated the
  `load` callback, re-firing the effect, flashing `GoalDetail` back to its
  `'loading'` early return — which unmounts whatever dialog is currently
  open mid-submission, discarding its local state. Fixed by depending on
  `props.goals.loadDetail`/`props.goals.loadHistory` directly (both
  `useCallback`-stable in `useGoals`, depending only on `gateway`/`spaceId`)
  instead of the whole `goals` object.
- **A redundant explicit `aria-label` on the "Target amount" `<label>`
  element** (in addition to its own text content, which already supplies
  the accessible name via native label association) gave the label element
  itself a competing accessible name, so `getByLabel`/`getByRole('textbox')`
  resolved two elements instead of one. Fixed by removing the redundant
  attribute — the wrapping `<label>` text alone was always sufficient,
  matching every other field in the same form.
- **`GoalMilestones`' checklist actions never triggered a re-fetch of the
  goal detail they belong to.** Every dialog (funding, purchase, edit)
  refreshes via its own `onClose` → `closeDialog` → `load()`, but the
  milestone list is inline, not a dialog, so nothing called `load()` after
  a successful `complete`/`reopen`. A real click showed the button label
  never updating even though the command succeeded server-side. Fixed by
  wrapping the `onSetMilestone` callback passed to `GoalMilestones` to call
  `load()` after any non-ambiguous outcome.

## Task 1 — Flow and fixtures

Goals mounts as its own `<GoalsCurrencySection>` inside `PlanRoutes`,
alongside the existing `PlanPage` and `AllocationCurrencySection` — not
replacing either, matching task 08's own "Allocation is a view within Plan"
precedent exactly. `GoalsPage` fetches the full relevant set once per
`(spaceId, currency)` with `stateFilter: 'all'` and filters client-side per
tab (`active`/`paused`/`closed`/`needs_review`/`all`) rather than
re-querying `goal_page` per tab click — reasonable given the DB's own
200-goal cap per space/currency bounds the list size. Every hook status
(`loading`/`ready`/`saving`/`accepted-refresh-pending`/`ambiguous`/`error`)
has a distinct rendered state, proved directly in
`goals-page.test.tsx`/`goal-detail.test.tsx` with a fake `GoalsState`, plus
a stale-response-discard-on-space-change test and a membership-loss test in
`use-goals.test.tsx` (already proved at the hook level in task 12; not
re-proved per-component here). "No direct progress editor" is upheld
structurally: nothing in `goal-detail.tsx`/`goal-editor.tsx` ever writes
`earmarkedMinor`/`coveredMinor`/`fulfilledMinor` directly — those fields are
always DTOs read back from the gateway, changed only by
reserve/release/move/link commands.

**Linking an existing purchase is reached from the goal's own detail page**
(`GoalPurchaseDialog`, pasting the expense's reference id), not from an
in-flow prompt inside the Wallets/Record transaction dialog — extending
that dialog is out of this task's owned files and would touch a different
feature's posting flow ("do not change... posting gateways"). This is a
documented, deliberate scope boundary, not an oversight; see
`docs/decisions.md`.

**U13-01 through U13-06** are covered as follows: U13-01 (cash70000 claims
60000/30000 → 60000/10000 coverage) and U13-04 (purchase 40000 from 100000
earmark → 60000 remaining, 40000 fulfilled) are encoded directly as e2e
fixture data and asserted on the rendered detail page. U13-02 (a wallet
transfer never inflates goal progress) holds structurally — the UI has no
code path from wallet data into any goal field, only from `GoalSummary`/
`GoalDetail`'s own DTOs — proved by a component test asserting the rendered
figures equal exactly the fixture's `earmarkedMinor`/`coveredMinor`, nothing
derived. U13-03 (reserve 20000 then release 5000 → 15000) and U13-05
(reversal restores earmark and updates an amount milestone) are already
exhaustively proved at the DB/gateway level (tasks 10–12); re-deriving the
exact SQL arithmetic through a mocked e2e fixture would test the fixture,
not the product, so this layer instead proves the *UI plumbing* (dialogs
call the right method with the right arguments, the screen reflects
whatever the gateway returns) via `goal-funding-dialog.test.tsx` and the
live "funding dialog reserves an amount" e2e test. U13-06 (checklist
complete never changes money) holds structurally — `set_goal_milestone_state`
is the only call `GoalMilestones` ever makes, and it carries no amount
argument at all.

## Task 2 — Screen and acceptance properties

Every value in `goal-detail.tsx`'s metrics grid is its own labelled cell
(target, earmarked, cash-covered — explicitly "Unknown" rather than 0 when
`coveredMinor` is null, fulfilled, shortage-before-bills, monthly target,
this month's net contribution) — never merged or inferred from another.
Horizon and the next incomplete milestone are shown together; a deadline
suggestion and pace forecast surface their own state
(`estimate`/`insufficient_history`/`no_positive_pace`/`beyond_horizon`)
with distinct copy per state. A closed goal with `needsReview` gets its own
banner and a "Reopen goal"/"Manage funding" action pair, and — deliberately
— a plain closed goal (no restored balance) shows no funding action at
all. Every dialog (`GoalFundingDialog`, `GoalPurchaseDialog`, `GoalEditor`)
follows `archive-wallet-dialog.tsx`'s exact shape: one submission path
(Enter or the primary button), disabled while pending (no double-submit),
an ambiguous outcome offers an explicit same-payload retry rather than a
second differently-shaped Save, and a recoverable rejection preserves
whatever the user typed (state is never cleared on error, only on success
or explicit cancel). `GoalFundingDialog` additionally catches
`underfunded_confirmation_required` specifically and offers "Reserve
anyway" (retrying with `acceptUnderfunded: true`), never silently
resubmitting. `GoalEditor`'s revise mode carries an explicit, honest warning
that `note`, the goal's own base monthly amount, and priority are not
pre-filled — `goal_page`/`goal_detail`'s summary (task 11's own exact field
list) does not expose them, and no SQL change is in scope here; see
"Known limitation" below. Pause/resume/close reuse the same editor with a
`state` radio pre-selected via `initialState`, keeping that same honest
warning visible for every full-definition resubmission rather than a
one-click action that could silently reset unseen fields.

## Task 3 — Progress bar

`GoalProgressBar` (inside `goal-detail.tsx`) uses `chartPercent` exactly as
given, computing progress as task 11's own definition (`covered` for a
reserve goal, `covered + fulfilled` for a purchase goal) against the
target. A `null` `coveredMinor` renders "Coverage is currently unavailable"
instead of an empty or zero-filled bar. Overage is computed from the
original `BigInt` values, never the clamped percent, and rendered as an
exact numeric amount ("+$X.XX over target") alongside the 100%-clamped
visual bar — proved with a 110% fixture (60000 covered + 50000 fulfilled
against a 100000 target → exactly $100.00 over). The bar is wrapped in a
minimal `<table>` with a visually-hidden caption as its accessible-table
equivalent; a single-goal progress value has no further breakdown to
drill into, unlike allocation's own multi-group bars.

## Known limitation (documented, not silently accepted)

`goal_page`/`goal_detail`'s summary (task 11) does not expose
`contributionMode`, the goal's own base `monthlyAmountMinor`, `note`, or
`priority` — `revise_goal_plan` requires the complete definition every
call, so `GoalEditor`'s revise mode cannot faithfully pre-fill these four
fields and shows an explicit warning instead of silently guessing. See
`docs/decisions.md` for the exact follow-up this leaves for a future task
(extending the projection layer, not something this UI-only task can fix).
