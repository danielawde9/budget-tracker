# Task 05 — Allocation commands evidence

**Deliverable:** exact apportionment arithmetic, `save_allocation_template`,
and `publish_allocation_month`, per
`docs/superpowers/plans/future-planning/05-allocation-commands-db.md`. Layer:
database only. No UI/gateway edit — task 05 explicitly exits before reads/UI.

## Process

Built test-first, one task at a time, against `tests/db/allocation-commands.integration.test.ts`
(44 tests): Task 1's exact arithmetic helper first (16 tests, including the
plan-pack review's 5,005-case largest-remainder conservation sweep, run as
one SQL round trip per weight vector via `generate_series` + `LATERAL`
instead of 5,005 separate network calls over the SSH bridge), then
`save_allocation_template` (14 tests), then `publish_allocation_month` (12
tests), then a seeded-upgrade test. Two real defects were found only by
running through the actual command path, not by reading the given SQL:

- **A deferred constraint trigger fires at COMMIT, outside any calling
  function's stack.** Task 04's seven trigger adapters were `SECURITY
  INVOKER`, correct for owner-seeded test rows (task 04's only path) but
  broken the moment a real `SECURITY DEFINER` command (`save_allocation_template`)
  did the insert: by the time the deferred trigger fired at commit, the
  session was back under the plain `authenticated` role, which has no
  `EXECUTE` on the revoked-from-everyone `check_allocation_template`/`check_allocation_month`.
  Fixed with `CREATE OR REPLACE FUNCTION` on all seven adapters (now
  `SECURITY DEFINER`); `20260914110000_allocation_schema.sql` is not edited.
  Full write-up: `docs/decisions.md` / [memory: deferred-trigger-security-context].
- **A `UNION ... ORDER BY` scoping mistake** ("missing FROM-clause entry for
  table 'revision'") in the complete-set-root query: an unparenthesized
  `SELECT DISTINCT ON (...) ... ORDER BY` as the second branch of a `UNION`
  attaches its `ORDER BY` to the whole union, where the table alias is out of
  scope. Simplified to a plain `SELECT category_id` (the outer `UNION`
  already deduplicates; no `DISTINCT ON`/`ORDER BY` was actually needed).
- A `jsonb_to_recordset` coercion issue in the upfront overallocation check
  (string-typed `amountMinor` not reliably coercing to `bigint` through that
  path) was replaced with the same direct `jsonb_array_elements` + `->>`
  extraction style used everywhere else in this migration.

Task 05 item 5 ("strengthen task 04's deferred check to compare exact helper
outputs, not just their sum") required `CREATE OR REPLACE` on
`private.check_allocation_month` — the aggregate sum+bps check alone could
not detect a snapshot whose per-group amounts don't match
`private.allocate_planning_income`'s real largest-remainder distribution as
long as they summed correctly. This directly changed the postconditions three
of **task 04's own tests** already relied on (they declared `group_count: 0`
while their fixture template actually has one 8000-bps group, which the old
sum-only check never noticed): fixed by adding the missing
`allocation_month_groups` row with the exact computed amount to each, in
`tests/db/allocation-schema.integration.test.ts`. This is expected
maintenance from a deliberate, spec-directed strengthening, not scope creep.

## Task 1 — `private.allocate_planning_income`

All of the task's named vectors pass, including the fact that the function
**always** emits a residual row (even at `target_minor=0`) — the task's own
"→112000/48000/40000/residual0" notation names four values, not three plus a
note that residual happens to be zero, as first misread. Also verified:
zero income, zero-weight groups, the maximum bounded amount without overflow,
duplicate IDs/orders, invalid UUID, JSON null, string/fractional `basisPoints`,
sum over 10000, and more than 12 groups.

## Task 2 — `public.save_allocation_template`

Proved: first save; exact replay (same request ID + payload → same result,
no new revision); stale `expected_revision_id` (`40001`); reusing an existing
group ID with the same purpose across revisions (no duplicate row); rejecting
reuse with a **different** purpose (`P0001`, using the correct current head
so the check under test — not an incidental stale-revision rejection — is
what actually fires); a root mapping to a subcategory, an archived category,
a group not included in this submission, and a future-purpose group (all
rejected); an unknown field on a group object; a duplicate `categoryId`
across root mappings; zero groups and zero root mappings (an explicitly
allowed empty template, matching the schema's own `group_count between 0 and
12`); outsider denial; and a real concurrency race
(`orderedAuthenticatedRace`) proving two template saves for the same space
serialize on the shared `lock_planning_actor` space lock.

## Task 3 — `public.publish_allocation_month`

Proved: first publish (income + one grouped root + a present-but-empty
standalone loan-pool row, since `loan_line_count` is always 1); exact replay;
stale `expected_snapshot_id` (`40001`); the complete-set rule rejecting an
omitted template-mapped root and an omitted existing positive manual target;
explicitly zeroing an old manual target to stop it (allowed); a root target
exceeding its spending group's computed target (upfront `P0001`, not just the
deferred backstop); a loan pool linked to a spending-purpose group (`P0001`);
a standalone loan pool accepted even while it would be "overallocated" (no
group to fit); the existing subcategory-root rejection propagating through
unmodified from `private.set_monthly_budget_plan`; outsider denial; and a
real race proving two publishes for the same month serialize on the space
lock, with the second correctly seeing the first as current and rejecting
as stale rather than silently overwriting it.
