# Task 11 — Goal coverage and monthly planning integration evidence

**Deliverable:** truthful cash coverage, monthly contribution, and
milestone-progress read model over task 10's commands (`goal_page`,
`goal_detail`, `goal_history_page`), plus one-time monthly-plan integration
(`allocation_month_goal_lines`, `publish_allocation_month_v2`, an extended
`allocation_month_state`), per
`docs/superpowers/plans/future-planning/11-goals-projections-db.md`. Layer:
database only. Depends on tasks 06 and 10. Closes Release 2's read side.

## Process

Split into two stages so real-Postgres feedback could land before the
larger, more invasive stage began: first the private
`goal_relevant_set`/`goal_coverage_set`/`goal_monthly_extras` helpers and the
three public read RPCs (`tests/db/goal-projections.integration.test.ts`, 19
tests, all green after four test-authoring fixes — no SQL defects), then the
monthly-snapshot integration touching task 04/05/06's already-committed
allocation objects (`tests/db/goal-month-integration.integration.test.ts`,
11 tests). The second stage found real SQL defects, caught by the real
disposable-Postgres run exactly as every prior DB task this session:

- `jsonb -> 'key'` on a JSON `null` value returns the *jsonb* value `null`,
  not SQL `NULL` — `v_entry->'groupId' is null` in
  `publish_allocation_month_v2`'s Future-group-linkage checks was always
  false for an explicit `null`, so a standalone (unlinked) goal target
  wrongly failed "must link to an included group". Fixed to the text
  extraction operator (`v_entry->>'groupId' is null`), which does collapse
  JSON `null` to SQL `NULL`, in both places this pattern appeared.
- `set_goal_monthly_target` (task 10) returns a single `jsonb` value
  (`{revisionId}`), not a `table(id bigint, …)` like
  `set_monthly_category_target`/`set_monthly_income_plan` — copying the
  roots' `select id into … from public.set_monthly_category_target(…)` call
  shape for goals raised `column "id" does not exist`. Fixed to
  `(public.set_goal_monthly_target(…)->>'revisionId')::bigint`.
- The forward-fixed `check_allocation_month`'s new over-allocation subquery
  referenced `month_group.snapshot_id` (an outer, non-grouped column) inside
  a correlated subquery under a `GROUP BY month_group.group_id,
  month_group.target_minor` — Postgres correctly refused it ("subquery uses
  ungrouped column"). Fixed to reference `p_snapshot_id` directly, since the
  outer `WHERE month_group.snapshot_id = p_snapshot_id` already makes them
  equal.
- Two test-authoring mistakes: a "closed with earmark" fixture reserved and
  immediately closed a goal without releasing first, hitting task 10's own
  "closing requires zero remaining earmark" guard (fixed to
  reserve→release→close→reverse-the-release, task 10's own established
  pattern for constructing a needs-review goal); and an old-publish
  omission test never advanced `p_expected_snapshot_id` past the seeded
  snapshot, so it hit the pre-existing stale-revision check before ever
  reaching the new goal-omission guard (fixed to pass the real snapshot id).

## Task 1 — Coverage, monthly contribution, milestone progress

`private.goal_relevant_set` counts before returning: more than 200 relevant
goals (active/paused, plus closed goals with a nonzero earmark) raises
`P0001` rather than silently truncating before coverage is allocated. Since
this state is unreachable through `create_goal_plan`'s own 100-active/
200-total caps (task 10), the test proves this independent read-side
defense by seeding rows directly — the same "simulate another layer's
failure" pattern CLAUDE.md asks for. `private.goal_coverage_set` implements
the task's own prior-claims window (`priority, created_at, goal_id`) exactly
as given, proved against the two-goal 70000-pool scenario from the task's
own Task 5 table (60000/10000, then 50000/0 once the pool drops by an
ordinary expense with no goal command involved) and against pagination
(identical coverage for a goal regardless of which page it lands on, since
coverage is computed once over the whole relevant set before paging).
`private.goal_monthly_extras` computes the declared monthly target, the
month's actual signed net earmark movement, a deadline-implied suggestion
(`ceil(remaining/months)`, `null` when overdue with remaining still
positive), and a three-completed-month pace forecast (`insufficient_history`
below three months of goal age, `no_positive_pace` for a non-positive mean,
`beyond_horizon` past 120 periods, otherwise `estimate` with a projected
month) — each state proved directly.

## Task 2 — Public RPCs

`goal_page` filters (`active`/`paused`/`closed`/`all`/`needs_review`) over
the relevant set, paginates by `(created_at, goal_id)` (a stable chronological
order independent of the priority order used internally for coverage),
rejects a partial cursor and an unauthorized caller. `goal_detail` resolves
an `amount` milestone's completion from `covered + fulfilled` progress
against its threshold and a `checklist` milestone's completion from its own
latest event — proved both ways — and returns `earmarkHead` (from
`goal_financing_state`) and `definitionHead` (the current revision id) for
optimistic concurrency. `goal_history_page` unions all six source kinds
(`definition`, `earmark`, `purchase_link`, `checklist`, `monthly_target`,
`financial_reversal`) into one keyset-paginated feed ordered
`(created_at, source_kind, source_id)` descending, rejecting a partial
three-part cursor.

## Task 3 — Monthly snapshot integration

`allocation_month_goal_lines` mirrors `allocation_month_roots`' shape
(nullable `group_id`, matching FK); `check_allocation_month` is
forward-fixed (`CREATE OR REPLACE`, task 04/05's own committed migration
file is not edited) a second time to add the goal-line count, each line's
exact amount against its own `goal_monthly_target_revisions` row, and
Future-only group linkage. `publish_allocation_month_v2` adds `p_goal_targets`
as a distinct function (never an overload of v1 with a default, per the
task's own instruction) with its own complete-set rule (every goal with a
currently positive monthly target must appear, a stopped target submitted
explicitly as zero) and its own Future-group-fit check (debt commitment plus
every linked goal target together must not exceed the group's own target).
`publish_allocation_month` (v1) is forward-fixed to refuse publishing over
an existing positive goal target it has no way to represent, so an old
client can never silently erase a goal's monthly commitment. `allocation_month_state`
is forward-fixed so a Future group's actual is debt paid plus the monthly
signed net earmark movement of every goal whose current target links to it,
and `leftToAllocate` subtracts standalone (unlinked) goal targets and a
Future excess generalized across every Future group (not only the single
loan-linked one) — proved that a group-linked goal target is counted once
(already inside that group's own basis-points share, not double-subtracted)
while a standalone one is subtracted directly.
