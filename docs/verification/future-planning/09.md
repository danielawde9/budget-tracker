# Task 09 — Goal and milestone schema evidence

**Deliverable:** constrained goals, full milestone definitions as children of
a versioned `goal_revisions` snapshot, checklist completion history, an
advisory earmark ledger, and purchase associations, per
`docs/superpowers/plans/future-planning/09-goals-schema-db.md`. Layer:
database only. No RPC/UI — task 09 explicitly exits before commands (task
10). No posting function is changed by this schema file. This opens
**Release 2** (goals: tasks 09–13), following Release 1 (allocation).

## Process

Built test-first against `tests/db/goals-schema.integration.test.ts` (35
tests) and `tests/db/goals-migrations.integration.test.ts` (2 tests), in the
task's own Task 1→2→3 order: table shapes, then the three deferred
cross-row checks, then security/grants. Every deferred-trigger adapter was
written `SECURITY DEFINER` and every constraint trigger given the
`_publish_check` naming suffix from the first draft — both lessons already
recorded from tasks 04/05 (see `docs/decisions.md`), applied proactively
this time. Result: **37 of 37 tests passed after fixing only two
test-authoring mistakes, zero real SQL defects** — the first task in this
roadmap where the real-Postgres run found nothing wrong with the SQL itself:

- A test asserted rejection on the bare `INSERT` statement for a violation
  that only a *deferred* constraint trigger catches; deferred triggers fire
  at `SET CONSTRAINTS ALL IMMEDIATE`/commit, not on the `INSERT` itself, so
  the assertion needs to wrap `forceDeferred()`, with the `INSERT` running
  unprotected just before it. Fixed to match every other deferred-violation
  test in the same file.
- A test asserted `TRUNCATE public.goals` gets rejected by
  `private.planning_reject_mutation`, but Postgres refuses to truncate a
  table with incoming `ON DELETE RESTRICT` references from other tables
  (`goal_revisions`, `goal_milestones`, `goal_earmark_events`,
  `goal_monthly_target_revisions` all reference `goals`) with its own
  `0A000` error *before any trigger runs at all* — stronger protection, not
  a gap. Fixed by testing `TRUNCATE` on a leaf table instead
  (`goal_earmark_lines`, referenced by nothing), which does reach the
  trigger.

## Task 1 — Table shapes

All nine tables (`goals`, `goal_revisions`, `goal_milestones`,
`goal_revision_milestones`, `goal_milestone_events`, `goal_earmark_events`,
`goal_earmark_lines`, `goal_purchase_links`, `goal_monthly_target_revisions`)
created exactly as given in the task file, including every inline `CHECK`,
composite `FOREIGN KEY`, and the initial/successor partial unique indexes
for `goal_revisions`, `goal_milestone_events`, and
`goal_monthly_target_revisions`.

## Task 2 — Deferred cross-row validation

**`private.check_goal_definition`** (on `goal_revisions` and
`goal_revision_milestones`) proved: a valid two-amount-milestone revision
with a consistent deadline; a mismatched `milestone_count` vs. actual
children (including a late child appended to an already-committed revision
from a separate transaction); a threshold exceeding the goal's target; a
decreasing threshold across ordinals; a decreasing due date across
ordinals; a due date past the goal's own deadline; predecessor-chain forks
(two initial revisions for one goal; two successors naming the same
predecessor).

**`private.check_goal_milestone_event`** proved: a valid `complete` action
on a checklist milestone in the latest definition; rejection when the
milestone is absent from the latest definition (dropped by a later
revision); rejection when the milestone is `amount`-kind, not `checklist`;
predecessor-chain fork (two initial events for the same milestone).

**`private.check_goal_earmark_event`** proved: valid `reserve`, `release`,
`move` (two goals summing to zero), and `reverse` (exact line-for-line
inverse of a non-reverse original) events; an event with fewer lines than
its declared `line_count` (including a late line appended to an
already-committed event from a separate transaction); a `move` whose lines
don't sum to zero; a `move` collapsed onto one goal; a second reversal of
the same original event (the `unique(reversal_of)` constraint); reversing a
reverse; a release that would drive a goal's effective earmark negative; a
reserve that would exceed the goal's target; and the specific scenario the
task calls out explicitly — lowering a goal's target below its existing
earmark does **not** retroactively invalidate the prior reserve, and a
same-goal release afterward still succeeds (proving the "only the
increasing side of an event is checked against the ceiling" design).

## Task 3 — Security and schema tests

One structural query proves RLS is enabled and zero
public/anon/authenticated/service_role privileges exist on all nine
relations at once (cheaper and less repetitive than nine near-identical
functional tests). Functional proof of the guard/immutability layers itself
uses `goals` (INSERT guard denies an authenticated insert even with a
temporary grant and permissive RLS; a zero-row `DELETE` is rejected) and the
leaf table `goal_earmark_lines` (`TRUNCATE` rejected), matching the density
of task 04's own precedent (which proved the pattern once, not once per
table, since the guard/reject functions are generic and table-agnostic).
